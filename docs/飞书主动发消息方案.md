# 飞书主动发消息方案

## 1. 目标

在气泡聊天、任务详情、需求工作台里，让当前这次运行给飞书里已经配对过的人发一条私聊。

1. 三个入口用同一套选人方式。输入 `@` 仍然默认选智能体；飞书联系人是同一个菜单里的「飞书」分类。
2. 选中的人变成一枚芯片。芯片是结构化数据，随消息单独提交。
3. 没有姓名也能选。列表第二行固定给出集成名和用户 ID，靠它区分没名字的人。
4. 发送权限只来自触发这次运行的用户消息。历史消息、任务描述、自动化、飞书入站消息都不授予权限。
5. 统一按 `open_id` 发私聊。同一个飞书应用和一个人之间的私聊只有一个，有没有聊过都进这一个会话。
6. 助手回复里能看到发给谁、发出去的原文；失败时能看到飞书返回的原因，并能一键重发。
7. 对方在飞书里回复，回复进收件箱里这个人的私聊。收件箱里能看到刚才发出去的原文。回复不回到发起的气泡、任务或工作台。

本文是实现方案，不表示这些能力已经完成。群聊、在飞书消息正文里 @ 某人，不在这一期。

---

## 2. 当前实现与缺口

### 2.1 已有基础

- 气泡和工作台都是 `ChatPanel`，任务详情是 `TaskActivity`。三处共用 `ChatComposer`。收件箱的普通条目也用 `ChatPanel`，任务类条目用 `TaskActivity`。任务描述和新建任务里还有一个只读或嵌入的 `ChatComposer`。
- `@` 打开建议菜单，默认分类是智能体。芯片种类在 `ComposerEntityKind`：`agent`、`squad`、`skill`、`mcp`、`task`、`requirement`、`session`。选中后插入引用芯片，发送时变成 `[实体引用] <kind> <id> <名字>` 文本，再由正则解析回芯片（`composer-content.ts`）。
- 一条用户消息里的 `[实体引用] agent|squad` 会变成这次要跑的目标（`explicit_chat_targets`）。没点名时，用会话自己的 `target_type` / `target_id`。点了小队时，`dispatch` 只启动队长。同一个智能体被点到多次，合并成一次运行；被点名的人如果就是这个小队的队长，保留队长那次运行。
- 队长在回答里用 `[@名字](mention://agent/<id>)` 派活，队员在同一会话里另起运行，回复对象是队长。队员都结束后，系统再唤起队长收尾。这些后续运行的 `parent_run_id` 指向上一级。
- 会话已经在跑、且这条消息没有点名别的智能体或小队时，消息走 `steer`，追加进当前这次运行，不新建 `run_id`。
- 飞书入站消息会记下 `chat_id`（`oc_`）和发送者 `open_id`（`ou_`）。出站回复只走入站时冻住的 `chat_id`。会话绑在集成配置的智能体或小队上，不绑在用户当时正打开的那个聊天上。
- 收件箱回发要等该会话里没有 `queued` / `running` 的运行，然后取最新一条 `assistant` 消息发出去（`channel/outbound.rs` 的 `deliver_pending`）。所以小队里飞书通常只收到队长收尾的那一条，不会按队员每人一条。
- `send_message_raw` 固定 `receive_id_type=chat_id`。用 `open_id` 发私聊，官方接口可以做到，产品里还没有这条路径。
- 授权用户存在 `channel_allowed_users`，有 `open_id`、角色、可选的 `display_name`。通讯录接口在权限范围内才返回 `name`；没返回时不写入空姓名。
- 智能体是 CLI 子进程。平台操作走 `multara` CLI，子进程环境里有 `MULTARA_RUN_ID`。写操作已经按 run 做权限检查（`ensure_write_allowed`）。
- 收件箱里来自飞书、且该线程已是历史只读的用户消息，输入框只读。还在等输入的线程，输入框仍然可编辑。

### 2.2 主要缺口

1. 输入框不能选飞书联系人，智能体也没有「发给这个人」的命令。在气泡里对智能体说「给某人发飞书」，只会在 Multara 里回答。
2. 出站不能按 `open_id` 发。没有入站会话记录的人，即使用户 ID 已知，也发不出去。
3. 姓名经常为空。不能把「有名字才能 @」当成选人的前提。
4. 收件箱会话和授权用户是两份数据。同一个人要合成一行，避免列表里出现两次。
5. 现有芯片发送时是纯文本，靠正则解析。飞书私聊进来的消息也会变成会话里的用户消息。收件人如果仍从文本里解析，对方打一行 `[实体引用] feishu …` 就能让智能体替他给别人发消息。收件人必须来自输入框提交的结构化数据。

## 3. 界面

### 3.1 菜单

在气泡、任务评论、工作台的输入框里输入 `@`。左侧分类在现有分类之后增加「飞书」。

这一分类只在有已启用的飞书集成时出现。下面这些输入框不出现该分类：收件箱（含还在等输入的线程）、任务描述、新建任务。

没有配对过的人时，右侧显示：「还没有配对的人。对方给机器人发过消息并完成配对后会出现在这里。」

每一行两行字：

| 行 | 内容 |
| --- | --- |
| 第一行 | 有姓名用姓名。没有姓名时显示「飞书用户 · 」加 `open_id` 末 6 位，例如「飞书用户 · 3f9a2c」 |
| 第二行 | 集成名 · 完整 `open_id`。有私聊时再附最近一次私聊的会话标题，例如「Multara 机器人 · ou_…3f9a2c · 最近：周会改期」 |

不用会话标题当名字。会话标题是按第一条入站消息自动生成的（比如「私聊 · 你是」），放在芯片上会被当成人名。

同一个人只出现一次。匹配规则：同一个集成下的同一个 `open_id`。收件箱里的私聊如果能对上这个 `open_id`，就把该会话的标题附到第二行，不另开一行。不同集成下的同一个人（`open_id` 按应用区分）各占一行，靠集成名区分。只在群里出现过的人，第二行不附群标题。

排序：最近有私聊往来的在前，其余按配对时间。主动发出去、对方还没回的，也算有往来，排在入站私聊同一规则里。

过滤跟现有菜单一样，匹配第一行和第二行。

### 3.2 芯片

选中后插入一枚芯片。`@` 智能体、`@` 小队的行为不变。

芯片上显示第一行的名字，前面加飞书图标。悬停显示完整的第二行（集成名、完整 `open_id`、有的话再加最近私聊标题）。

芯片上的数据：

- 集成 ID
- `open_id`
- 展示名（姓名或「飞书用户 · 末 6 位」）

一条消息可以带多枚飞书芯片。同一集成、同一个 `open_id` 放两次，按一个收件人算。智能体、小队、文件和其他实体芯片照旧。

芯片随消息以结构化字段提交，和正文分开存，不进入 `[实体引用]` 文本。手打或粘贴一段看起来像飞书芯片的文字，不算收件人。

已配对的人不再弹确认框。发送前芯片已经标明收件人，发出去的原文在结果卡里可见。

### 3.3 三个入口和收件箱

选人菜单在 `ChatComposer` 里。任务详情不经过 `ChatPanel`，分类的显示条件要放在输入框自身，不能只改 `ChatPanel`。

收件箱不提供这套选人。历史只读的线程仍然只读。要再联系这个人，回到气泡、任务评论或工作台，用 `@` 选他。

## 4. 正常流程

以气泡里、会话目标是一个智能体、只选了一个飞书联系人为例。任务评论和工作台走同一条路径。

1. 用户输入 `@`，在「飞书」里选中张三，写下「跟他说，明天的会改到三点」，发送。
2. 这条用户消息发给当前会话的智能体，此时还没有飞书消息。
3. 后端把芯片存到这条用户消息上，并写成这次运行的收件人名单：`feishu:1` 对应张三的集成 ID 和 `open_id`。
4. 给模型的提示词里只有句柄和展示名，并写明这是允许名单：按用户这句话决定发给谁，没有点名的不发。模型调用 `multara feishu send --to feishu:1 --text "明天的会改到三点"`。
5. 命令用 `MULTARA_RUN_ID` 核对名单，确认张三仍在该集成的授权用户里，然后以 `receive_id_type=open_id` 发私聊。
6. 飞书返回 `message_id` 和这个私聊的 `chat_id`。发送记录记下原文、状态和这两个 ID。
7. 用返回的 `chat_id` 找到收件箱里的私聊。没有就按入站的绑定规则新建：会话目标用这个集成配置的智能体或小队，标题用「私聊 · 张三」。已有会话不改标题。
8. 往该私聊追加一条代发记录，内容是飞书正文。这条记录不启动运行，也不写入 `channel_run_deliveries`。
9. 气泡里的助手回复下方出现结果卡：发给张三、原文、以及「在收件箱查看」。
10. 张三在飞书里回复。回复按现有入站进收件箱这条私聊，由集成绑定的目标来答，并按现有规则回发到这个私聊。气泡里的会话不再收到这条回复。

代发记录在收件箱里展示为已发出的消息，模型上下文里只放飞书正文，不放来源会话名。来源会话名经常是气泡里的第一句话，集成上的智能体可能把它回给飞书。

回发飞书时选取的「最新一条助手消息」要跳过代发记录。现有查询不区分消息种类，代发记录若被选中，会把同一段文字再发一遍。

## 5. 发送

### 5.1 收件人怎么交给智能体

新建运行时，把触发它的那条用户消息上的飞书芯片抄进这次运行的名单。每人一个句柄：`feishu:1`、`feishu:2`……编号按芯片在消息里的顺序，去重之后递增。

提示词只在这次运行有名单时出现：

```
本条消息允许发给以下飞书联系人。按用户的话决定发给谁，没有点名的不要发：
- feishu:1 张三（Multara 机器人）
发送：multara feishu send --to feishu:1 --text "<正文>"
发送由本次运行执行。
```

模型看不到 `open_id`。没有芯片的消息，提示词里不出现这一段。

`steer` 追加进同一次运行时，把新消息上的芯片并进当前名单，并在追加给模型的文本里带上同样的允许名单。这次运行里已经有的句柄继续有效，直到运行结束。点名了别的智能体或小队时不走 `steer`，芯片只进新建的那些运行。

### 5.2 命令

新增 `multara feishu send --to <句柄> --text <正文>`。CLI 用 `MULTARA_RUN_ID` 沿 `parent_run_id` 找到这次派活链的根运行，再查根运行上的名单。

以下情况直接拒绝，返回一句模型能看懂的原因：

- 没有 `MULTARA_RUN_ID`，或根运行没有名单（用户没放芯片、终端里手动执行、飞书入站、自动化、任务重试）
- 句柄不在名单里
- 收件人已不在该集成的授权用户里，或集成未启用，或不是飞书
- 正文为空或只有空白
- 正文长过现有回发的单段上限（`split_message` 使用的 18000）。这一期不拆成多条
- 这个句柄在这棵运行树上已经有一条成功发送
- 运行模式是 Plan

每个句柄在一棵运行树上只允许一条成功发送。失败不占这个名额，模型可以改完正文再调一次。用户要就同一人发第二条，需要新发一条带芯片的消息。

任务详情里，名单来自这次提交的评论。任务描述里的芯片不生效，那个输入框也不提供飞书分类。

### 5.3 路由

所有主动发送都用 `receive_id_type=open_id`。`send_message_raw` 改为接收 `receive_id_type`。现有入站回复继续传 `chat_id`。`open_id` 不能塞进 `chat_id` 参数。

这一期只发私聊纯文本。不发群、不在飞书正文里 @ 其他人、不发卡片和文件。

返回的 `chat_id` 用来找或建私聊绑定。这个人此前只有群会话时，不把代发记录写进群，按返回的私聊 `chat_id` 另建一条收件箱私聊。

### 5.4 结果卡

助手回复下方按发送顺序挂结果卡，数据来自该运行树上的发送记录，刷新后还在。

- 成功：展示名、集成名、原文。「在收件箱查看」用发送记录上的 `chat_id` 打开私聊。会话没建成时不显示这个入口，结果卡仍在。
- 失败：飞书返回的原因、原文、「重新发送」。

「重新发送」用这条失败记录里的收件人和原文直接调用后端，不经过模型，也不占成功名额。发出前再次检查授权和集成状态。这个句柄后来已经成功发过，按钮不再出现。授权已撤销时按钮置灰并说明原因。

## 6. 边界

### 6.1 多个飞书收件人

芯片是允许名单，不是「每个都发」。用户写「跟张三说」，消息里同时有李四的芯片时，只应发给张三。李四的句柄调用会被接受（他在名单里），所以提示词要写明没点名的不发。

每个成功发送各有一张结果卡、各写一条收件箱代发记录。两个收件人是两条私聊。

### 6.2 同一条消息 @ 了多个智能体

`dispatch` 给每个被点名的智能体各起一次根运行，同一个人合并成一次。每棵运行树各有一份名单，成功名额各自计算。

两个智能体都执行了发送时，对方会收到两条飞书消息。结果卡挂在各自的助手回复下。这是用户点了两个人的结果，后端不去重。

点名的人里包含一个小队，并且另一个被点名的智能体就是该小队队长：合并成队长那一次运行，名单只有一份。被点名的是队员、不是队长：队长一次、队员一次，各能成功发送一条。

### 6.3 会话目标是小队

用户没有另行点名时，只启动队长，名单挂在队长这次根运行上。

队长用 `[@队员](mention://agent/…)` 派活后，队员运行和队长的收尾运行都沿 `parent_run_id` 使用同一份名单、同一个成功名额。先调用成功的那次把名额用掉，后面的调用收到「已经发过」。

提示词写明发送由本次运行执行。队长应自己调用命令。队员拿不到名单之外的人，也不能在队长已经发成功之后再发一条。

队员之间的 @ 回复留在 Multara 会话里。主动发到飞书的只有命令送出的那段正文，队长在气泡里的说明文字不会再抄一份到飞书。

### 6.4 对方回复时，集成绑定的是小队

收件箱会话的目标是集成上的小队，不是气泡里发起代发的那个智能体。对方一回复，现有入站启动队长；队长可以再 @ 队员。

回发仍走现有规则：会话里还有未结束的运行时不发；全部结束后，把最新一条助手消息发回这个私聊。队员回复的对象是队长，飞书上通常只看到队长收尾的那一条。

这次入站运行没有飞书名单。队长、队员和收尾运行都不能再主动给第三个人发飞书。对方回复也不会回到当初那条气泡、任务或工作台。

### 6.5 运行中又发一条带芯片的消息

当前智能体还在跑，新消息没有点名别人：走 `steer`。新芯片并进当前名单，追加文本里带上句柄。模型这时才看得到新的收件人。

新消息点了别的智能体或小队：当前运行的名单不变，芯片只给新建的运行。

### 6.6 其他拒绝

- Plan 模式拒绝发送。
- 飞书入站、自动化、任务重试、没有 `MULTARA_RUN_ID` 的终端调用，都没有名单。
- 收件箱输入框和任务描述不能选出芯片。已经写进描述里的文字不产生名单。
- 集成在发送前被停用，或对方被移出授权用户：命令失败，结果卡上的重发按钮置灰。

## 7. 数据

不新建联系人表。一行联系人由现有数据拼出来：

- 授权用户提供 `open_id`、姓名、角色、所属集成
- 该集成下这个 `open_id` 的私聊绑定，提供会话标题，供第二行展示
- 主动发送成功后写下的私聊绑定，同样参与「最近往来」排序和第二行标题

姓名仍然只在通讯录接口返回非空 `name` 时写入。空姓名、会话标题、「飞书用户 · 末 6 位」都不写入授权用户的姓名字段。

需要新增的存储：

| 内容 | 键 | 用途 |
| --- | --- | --- |
| 用户消息的飞书芯片 | 消息 ID | 结构化收件人，不从正文解析 |
| 运行的收件人名单 | 根 `run_id` + 句柄 | CLI 把句柄换成集成 ID 和 `open_id` |
| 发送记录 | 根 `run_id` + 序号 | 句柄、收件人、原文、状态、失败原因、`message_id`、`chat_id`；结果卡和重发都读这里 |
| 收件箱代发记录 | 私聊会话 ID | 展示已发出的正文。单独的消息种类，回发查询跳过它，不对应一次运行 |

新建私聊会话时复用入站的绑定：键是集成 ID 加 `chat_id`，`target_type` / `target_id` 取集成配置。标题用「私聊 · 展示名」。

---

## 8. 不做的事

- 不在 `@` 里用一段纯文字表示飞书联系人，也不从正文解析飞书芯片。
- 不从收件箱的历史消息里直接再发。收件箱不提供飞书选人。
- 不给未配对的人发。列表里没有的人，命令也拒绝。
- 不让历史消息、任务描述、自动化或飞书入站消息授予发送权限。
- 不把代发记录走 `send_channel_message`，也不把它写成一条等回复的用户消息。
- 不做群聊，不做飞书消息正文里的 @，不发卡片和文件，不把超长正文拆成多条。
- 不因为姓名为空而隐藏这个人，也不要求用户先手填 ID。
- 不把同一个句柄在一棵运行树里的成功发送合并成「后端自动去重后再发」。名额用完就拒绝，由结果卡说明已经发过。
