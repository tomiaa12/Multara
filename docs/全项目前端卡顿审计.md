# 全项目前端卡顿审计：会影响体验的地方

范围：除聊天主链路和 Monaco 编辑器核心（已在《工作台卡顿分析.md》里分析并修复）之外的整个前端，以及 Rust 到前端的 IPC。

方法：按区域分三路只读排查（工作台终端 / 文件树 / 搜索 / SCM；视图 / 状态 / 启动 / 打包；CSS / IPC / 同步命令），每条结论带文件位置。我对其中影响最大的几条回到代码里核对过，下面用 **[已核对]** 标出；其余是排查时读代码得出、我没有再逐条复核的，标 **[排查所得]**；没有实测只是按机制推断的，标 **[推断]**。

**这份文档没有改任何代码，也没有做性能录制。** 所有“慢”都是按代码复杂度和触发条件判断的，不是实测耗时。

严重程度：**高** = 在常见规模下就会明显卡；**中** = 大仓库 / 大数据量 / 特定操作下卡；**低** = 影响小或只在极端情况。

## 1. 终端

### 1.1 每个数据块一个 IPC 事件，没有合并和背压（高）[已核对]

`src-tauri/src/terminal.rs:123-137`：读线程 `reader.read(&mut buffer[8192])` 之后立刻 `app.emit("terminal-data", { id, data: base64(...) })`。没有合并、没有节流。`yes`、`cat` 大文件、编译输出会每秒产生成千上万个事件。

前端不会让 PTY 暂停，所以输出比渲染快时，xterm 的写队列会一直涨。解码用 `Uint8Array.from(atob(data), c => c.charCodeAt(0))`，逐元素回调，慢。

### 1.2 每个数据块都重建标签数组（高）[已核对]

`TerminalPanel.vue:581-590` 里 `term.write(binary, cb)` 的回调会 `emit("patch", id, { busy })`，对应 `WorkspaceWorkbench.vue:3267`：

```ts
function patchTerminal(id, patch) {
  terminalTabs.value = terminalTabs.value.map(item => item.id === id ? { ...item, ...patch } : item);
```

即使 `busy` 没变，也为每个数据块分配新数组和新对象，并触发所有依赖 `terminalTabs` 的 watcher / computed。

### 1.3 同一个数据块被解码两次（中）[排查所得]

`stores/running-terminals.ts:93-102` 还有一个全局 `terminal-data` 监听，对被追踪的终端再解码一遍；`pushScrollback` 每次 `reduce` 求和并 `shift()`，256KB 上限、8KB 一块时每次扫描约 32 块。

### 1.4 每 2 秒起一次子进程（中）[排查所得]

`running-terminals.ts:76-86` 只要有被追踪的终端，每 2 秒调 `terminalServices()`，Rust 侧会 `ps -ax` 加监听端口扫描。在后台线程跑，不卡界面，但持续耗 CPU / 电，窗口隐藏时也不停。

### 1.5 发布终端内容时全量扫描滚动缓冲（中）[排查所得]

`TerminalPanel.vue:905-930`：400ms 防抖后循环整个缓冲区（滚动缓冲 5000 行）做 `translateToString`，只保留最后 4000 行再发 IPC。每次输出停顿、切标签、改高度都会触发。

### 1.6 WebGL 上下文和拖拽重排（中）[排查所得]

- 每个终端会话一个 `WebglAddon`，没有 `onContextLoss`。浏览器通常只允许约 16 个 WebGL 上下文，终端标签很多时会静默丢上下文。
- 拖动面板或分隔条的每次 `pointermove` 都会 `fit()` 并向后端发一次 resize，shell 会被反复发 SIGWINCH（逐次调用频率为推断）。

## 2. 文件树

### 2.1 每次目录刷新整棵树重建（高）[排查所得]

`WorkspaceWorkbench.vue:996-1045` 的 `explorerRowsByWorkspace` / `visibleExplorerItems` 依赖 `directoryChildren`、`expandedDirectories`、`workspaceRoots`。每次目录重载（整体替换 `directoryChildren`）都重新为每个条目分配行对象、逐层排序、`compactChain` 重走子节点，再展平一遍。行是递归渲染的，**没有虚拟化**。

触发：展开了几千个节点；或 AI 持续写文件（文件监听每 500ms 合并刷新一次）。

### 2.2 每一行 3~4 次对全部 git 变更做 filter（高）[已核对]

`WorkspaceWorkbench.vue:1553-1570` 的 `treeGitStatus`，目录分支：

```ts
statuses.filter(change => change.path === entry.path || change.path.startsWith(prefix)).map(gitStatusLetter)
```

模板里每行按 class / 徽标 / 文字 / title 各调一次，约 3~4 次，复杂度 O(行数 × 变更数 × 3)。

触发：仓库里有几千个变更（比如没忽略的构建产物），文件树又很大。

### 2.3 溢出事件触发全量重列（中）[排查所得]

文件监听事件溢出（`git checkout`、`npm install` 时超过 500 个路径）会让 `loadWorkspaceRoots({ preserve: true })` 重新列出所有已加载目录，再把全部路径重新排队做 gitignore 判断。

### 2.4 忽略集合克隆和逐级回溯（低~中）[排查所得]

`use-explorer.ts:1020-1043`：每次 flush 克隆整个 `Set` 并替换深响应式对象，每行渲染时 `isIgnored` 还要向上走祖先。单独影响小，会放大 2.1 和 2.2。

### 2.5 后端这一侧是好的

`explorer_fs.rs` 里 75ms 防抖、单批上限 500 条、200ms 节流、`overflow` 标志；前端 500ms 合并，git 刷新有 1 秒防抖加 5 秒冷却；监听都有清理。

## 3. 搜索与快速打开

### 3.1 搜索不防抖、不能取消（高）[已核对]

`SearchView.vue:96-98`：`watch(options, runSearch, { deep: true })`，而 `options.query` 是输入框的 `v-model`，文件里没有任何防抖。每次按键调用 `backend.searchWorkspace`，Rust 在 `spawn_blocking` 里做一次完整目录遍历（`text_search.rs`）。前端只靠 `request` 序号丢弃过期结果，**后端的遍历不会被取消**。

触发：在大仓库里打一个 6 个字的查询，会同时有最多 6 个全树 grep 在跑。

### 3.2 结果渲染（中）[排查所得]

最多 2000 条匹配用 `v-for` 渲染，无虚拟化；`resultRows(...)` 是模板里直接调用的函数而不是 computed，任何重渲染（选中、折叠）都会重算；里面有 `dirs.set(name, [...(dirs.get(name) ?? []), file])` 这种每个目录 O(n²) 的拷贝；`matches` 是 2000 个对象的深响应式 `ref`，可以用 `shallowRef`。

### 3.3 快速打开每次按键全量排序（中）[排查所得]

`quick-open.ts:43-62`：每次按键对全部文件 `replaceAll` + `toLowerCase` + `split("/")` + 排序（平局用 `localeCompare`），无防抖；文件列表在工作台里是深响应式 `ref`。

触发：5 万文件以上的仓库。

## 4. 编辑器周边（不含已修的 Monaco 核心）

### 4.1 大纲每次按键对全文重算（高）[排查所得]

`src/editor/outline.ts` 的 `outlineFromContent` 通过 `activeOutline`（`WorkspaceWorkbench.vue:722`）依赖 `activeFile.content`，每次按键重算：逐行最多约 10 个正则；每个大纲项的 `symbolEndLine` 还会再对全文 `split` 一次，复杂度 O(符号数 × 行数)。

触发：5000 行以上、几百个符号或标题的文件。同步在主线程。

### 4.2 缩进检测、待审文件列表、`dirty`（中）[排查所得]

`WorkspaceWorkbench.vue:701-717`、`785-805`：`detectIndent` 对全文 `split`（其实 80 行就够）；`pendingDiffFiles` 每次内容变化重建所有标签内容的 `Map` 再做 diff 判断；`dirty` 对全文做字符串比较；每次移动光标都 `syncEditorDocument`，并逐元素比较大纲数组。

### 4.3 Markdown 预览整篇重渲染（低）[排查所得]

`MarkdownPreview.vue:14-19`：`marked.parse` + `DOMPurify` + `v-html`，内容一变就整篇重来。只在预览模式可见时发生；上游是否防抖没有核对。

### 4.4 本地历史同步序列化整库（中）[排查所得]

`local-history.ts`：记录 / 列出 / 删除都对 `localStorage` 里**整个库** `JSON.parse`，写入时整库 `JSON.stringify`。上限 200 条、每条最多 20 万字符，最坏约 40MB 字符串，每次保存同步处理；时间线面板每次 `historyTick` 也会重新解析。

## 5. 源代码管理（SCM）

- 文件列表无虚拟化，`rowsFor` 在模板里直接调用，`selected.has` / `filesFor` 用 `.find` / `.filter`；`gitRepositories` 是包含所有变更的深响应式 ref（低~中）[排查所得]。触发：几千个变更或未跟踪文件。
- AI 连续写文件时，每个文件事件批次都会安排 `refreshGitViews`（冷却约 6 秒一次），结果整体替换 `gitRepositories`，会反复触发 2.2 的重算（低~中）[排查所得]。

## 6. 视图、状态与导航

### 6.1 `keep-alive` 缓存了最多 24 个页面（高）[已核对]

`App.vue:502-506`：

```vue
<keep-alive :max="24">
  <component :is="Component" :key="route.path" />
```

每个访问过的路径都会留着，包括每个任务各自的任务详情页。被缓存（deactivated）的组件**仍保留响应式副作用**，`store.data` 或 `runStates` 一变，所有缓存页都会在后台重渲染；`onBeforeUnmount` 在 deactivate 时不触发，所以里面的定时器不会停，例如 `TaskActivity.vue:121`、`RunLogDialog.vue:151` 各有一个 1 秒定时器 [排查所得；“deactivated 组件仍响应”是 Vue 行为，我没有在本项目里实测]。

触发：来回浏览十几个任务 / 页面，然后有运行在流式输出。

### 6.2 任务看板（高）[已核对]

`task-board.ts:35` 的 `taskCode(task, tasks)` 每次调用都 `[...tasks].sort(localeCompare)` 再 `findIndex`，而模板里（`TasksView.vue:461`）**每张卡片调用一次**，整体 O(n² log n)。`columnTasks(column.id)` 每列每次渲染调用 3 次（`TasksView.vue:434, 446, 469`），每次再排序一份副本。拖拽时 `dragover` 每次改 `dropBeforeId`，整个看板重渲染，上面这些全部重复一遍 [排查所得]。

触发：500 个任务。

### 6.3 任务筛选（高）[排查所得]

`TasksView.vue:78-95`：`tasks.filter(task => sessions.find(...))` 是 O(任务 × 会话)。启用标签筛选时，每个任务调一次 `readTaskMeta`，而它（`task-meta.ts:51`）**每次都对 `localStorage` 里的整个 blob `JSON.parse`**（`readTaskMeta` 的实现已核对）。1000 个任务就是 1000 次整库解析，且每次重算都来一遍。

### 6.4 整数组替换式刷新（高）[排查所得]

`stores/app.ts:644-660`、`:207`、`:314`：每次运行状态变化都 `refreshTaskInboxSurfaces()`，整体替换 `data.tasks / sessions / inbox`；每个终态运行还会 `refreshAgentsAndSquads()` 替换智能体和小队数组。深响应式 ref 下整数组替换会让所有消费者重渲染，刷新期间如果又有排队请求还会再拉一轮。

触发：多个并发运行（比如自动化任务），每次开始和结束都全量替换。

### 6.5 其它列表（中）[排查所得]

- 项目首页 `project-home.ts:93-149`：`rows` 对每个项目过滤全部工作区和会话、排序、扫描 `runStates`，复杂度约 项目 × 会话 × 运行；任何 `runStates` 或 `data` 变化都重算。
- 智能体集合 `CollectionView.vue`：每行 `agentStatusKey` 扫 `runStates`（每行调 2 次），`agentTaskCount` 对每行过滤全部任务；此页还被路由静态引入。
- 收件箱 `InboxView.vue`：普通 `v-for` 无分页；每次替换都复制排序；每行 3 次 `sessions.find + agents.find`。
- 任务详情 `TaskDetailView.vue:104-117`：watcher 读 `last.content.length`，流式输出时每个片段触发一次，再强制布局滚到底；`keep-alive` 下页面不在前台也会跑。

### 6.6 运行日志弹窗（中）[排查所得]

`RunLogDialog.vue:522`、`build-run-log.ts:382-397`：`<pre>` 渲染完整工具输入 / 输出，不截断，几 MB 的输出会产生单个几 MB 文本节点；搜索框每次按键对每个步骤 `JSON.stringify(input)`；`steps / lanes / rows` 在 payload 变化时全量重算；行列表无虚拟化。

### 6.7 其它小项

- 看板分类 `categories` 在 `categoryTick` 变化时重新解析 localStorage（低）。
- 侧栏 `navGroups` 在路由或收件箱变化时对每项调 `t()`（低，推断）。

## 7. 启动与打包

以下数据来自 `dist/assets`，那是 **10 月 23 日的旧构建**，只能看量级，不代表现在的大小 [排查所得]。

## 8. CSS 与渲染成本

整体干净：没有 `backdrop-filter`、`filter: blur`、`transition: all`、`text-shadow`、`mask-image`、SVG 滤镜；窗口不透明、没有 vibrancy（`tauri.conf.json` 里 `backgroundColor: #121212`）。

### 8.1 自绘滚动条是 JS 驱动，会强制同步布局（中）[已核对]

`src/ui/overlay-scroll.ts:110-117`、`228-262`：每个 `.vs-scroll` 宿主挂一个 `ResizeObserver` 和一个 `MutationObserver({ childList, subtree, characterData })`。每次 scroll 事件、每次子树 DOM 变化都进 `render()`：先改 transform，再读 `clientHeight / scrollHeight / scrollTop` 和两次 `getComputedStyle`，**每帧一次强制同步布局**。

触发：流式输出的聊天记录、终端 / 日志列表在 `.vs-scroll` 里时，每个新增 token 或节点都触发一次。这可能是 CSS 与渲染这一块里影响最大的点，聊天流式的放大效应是推断，代码机制已核对。

### 8.2 无限闪烁的文字高亮在主线程重绘（中）[排查所得]

`src/design/components.css:2242`：`UiShimmerText` 的 `.ds-text-shimmer` 用 `background-clip: text` 加 `animation: ds-shimmer 1.6s linear infinite`，只动画 `background-position`。这是绘制属性动画，无法合成，每帧都在主线程重绘该文字层。默认 `active=true`，没有可见性暂停。屏幕上同时有多个（比如每个运行中的步骤一个）时就是持续 60fps 重绘。已处理 `prefers-reduced-motion`。骨架屏 `.ds-skeleton`（`components.css:2129`）同类，只在骨架行上。

### 8.3 `:has()` 选择器（低~中，推断）

`styles.css:5266, 5294, 5412, 5415` 的 `.editor-area:not(:has(.editor-tab))` 等作用在包含 Monaco 的子树上；`styles.css:5630` 的 `.monaco-editor .margin-view-overlays div:has(> .dirty-diff-glyph)` 在 Monaco 滚动重绘边距时会反复匹配。WKWebView 对 `:has` 失效范围的处理是否更弱没有验证。

### 8.4 定时器驱动的重渲染（低）[排查所得]

- `ChatPanel.vue:375` 与 `TaskActivity.vue:121`：运行期间每秒更新 `liveClock`，所有读它的计算属性每秒重算。
- `MessageFooter.vue:34`：每条消息页脚一个 30 秒定时器，N 条消息就是 N 个。
- `WorkspaceWorkbench.vue:2389`：我加的 10 秒 `writeLockClock`，卸载前不停，会重算 `filesBeingWritten`。

### 8.5 其它

## 12. 补充核对：上一轮标成“没核对”的几项

- **`backend.ts` 里的循环**：我 grep 了 `for (` / `.map(` / `forEach` / `Promise.all`，命中的 282、922、1007、1255、1708 行都是预览数据或纯映射，**`backend.ts` 本身没有在循环里调 `invoke`**。真正的“循环里逐个读文件”出在调用方，见下一条。

我抽查核对过的有：Windows 的 `open_external_url`、终端快速修复的命令拼接、Emmet `*N` 无上限、三处粘贴图片的 `Array.from`。其余是排查所得（**[排查所得]**）或推断（**[推断]**）。

### 13.1 高

1. **粘贴 / 拖入大图会冻结界面并飙内存（高）[已核对]**：`ChatPanel.vue:910`、`views/TaskCreateDialog.vue:179`、`views/TaskActivity.vue:176` 都是 `const bytes = Array.from(new Uint8Array(await file.arrayBuffer()))`，**然后才**检查 `bytes.length > 25MB`（`ChatPanel.vue:911`）。一张 25MB 的图会先变成 2500 万个元素的 JS 数组（约 200MB），再变成 100MB 以上的 JSON IPC 载荷传给 `backend.savePastedAttachment(bytes, …)`，超限文件是付完代价才被拒绝的。改法：先看 `file.size`；IPC 传 base64 或二进制，不要用数字数组。
2. **Windows 命令注入 `open_external_url`（高，Windows 才受影响）[已核对代码；`cmd.exe` 行为为推断；项目发布了 nsis / msi 安装包]**：`src-tauri/src/commands.rs:3683-3706` 用 `cmd /C start "" <url>`，只检查前缀 `http://` / `https://`，Rust 不会为 `cmd.exe` 转义 `&`、`|`、`^`，形如 `https://x.y/?a=1&calc.exe` 的 URL 会让 cmd 把 `calc.exe` 当作第二条命令执行。前端把关 `backend.openExternalUrl`（`services/backend.ts:860`）同样只看前缀。可达的 URL 来源：智能体 / MCP 的 Markdown 链接、终端里 Ctrl 点击（`TerminalPanel.vue:526` 的 `WebLinksAddon`）、`MarkdownPreview.vue:41`、终端快速修复的 `openUrl`（`terminal-quick-fix.ts:41`，来自终端输出）。

## 14. 第三轮补充：剩余视图、`WorkspaceWorkbench.vue` 的保存流程、本地历史

我抽查核对过的有：`local-history.ts` 的 `writeStored` 没有 try/catch、`saveTab` 的保存流程、`applyDiskToOpenTab` 在文件消失时关闭标签。`WorkspaceWorkbench.vue` 这一路只读了约 15%（5900 行里的保存、磁盘变化、键盘与计时器相关段落），其余仍没读；几个视图也只读了一部分，范围见 14.5。

### 14.1 会丢用户数据的问题（比卡顿更值得先看）

1. **保存会在文件已经写入磁盘之后失败，标签永远显示“有未保存修改”（高）[已核对]**：`WorkspaceWorkbench.vue:3722-3750` 的 `saveTab` 在同一个 `try` 里先 `await writeWorkspaceFile(...)`，再 `recordLocalHistory(...)`；而 `local-history.ts:37` 是

   ```ts
   function writeStored(entries) { localStorage.setItem(STORAGE_KEY, JSON.stringify(entries)); }
   ```

   **没有 try/catch**。历史上限是 `MAX_ENTRIES = 200` × `MAX_CONTENT = 200_000` 字符，最坏约 40MB，而 `localStorage` 配额通常约 5MB。配额一满，一次**已经成功的保存**会抛 `QuotaExceededError`，`saveTab` 报错并返回 false，`tab.original` 和 `userEdited` 都不更新，标签一直是脏的，`refreshGitViews` 也被跳过；关闭、全部保存、git 面板里的“保存脏文件”流程都把 false 当成取消，用户被卡在一个假的“有未保存修改”标签上。
   - 影响面更大：配额一满，所有**没有 try/catch 的 `localStorage` 写入**都会坏：`stores/chat-open-tabs.ts:23` 的 `persistOpenTabsMap`、`saveRequirementCategories`、`App.vue:118-119` 的侧栏写入、`SideNav.vue:84`。
   - 修法：`writeStored` 包 try/catch，失败时淘汰最旧的条目再试；同时 `recordLocalHistory` 不要放进保存的 `try` 里。
2. **保存期间新敲的字被标记成“已保存”（高）[已核对]**：`saveTab`（`3732-3747`）里 `file` 是**实时的** `activeFile.value` 对象，`onEditorContentChange` 会原地修改 `file.content`；`await writeWorkspaceFile(..., file.content)` 写入的是 await 之前的文本，**await 之后**再 `tab.original = file.content`、`originalContent.value = file.content` 时读到的是已经变长的内容。结果：await 期间敲的字被当成“已保存的基线”，而磁盘上其实是旧文本；标签显示干净，关闭提示被跳过，`recordLocalHistory` 存的也是错的内容。修法：await 之前先 `const content = file.content`，之后都用它。
3. **磁盘文件消失时，有未保存修改的标签被静默关掉（中）[已核对]**：`WorkspaceWorkbench.vue:~3783` 的 `applyDiskToOpenTab`：`if (missing) { editorTabs.value = editorTabs.value.filter((item) => item !== tab); ... }`，**没有脏检查**；调用者 `reconcileOpenEditors` 在 git 丢弃和 `@worktree-changed`（比如切分支）时运行。文件被外部删除而用户正在改它，标签和未保存的修改会一起悄悄消失。`paths = []` 时它还会顺序重读所有打开的标签。
4. **技能详情页的草稿被后台刷新清掉（中）[监听器已核对；刷新行为为推断]**：`SkillDetailView.vue` 的 `watch(skill, () => { ... openFile.value = null; selectedPath.value = ""; ... })` 在计算属性 `skill` 返回新对象时触发；`saveFile` 保存 SKILL.md 后调用 `store.refreshResources()`，任何后台资源刷新都会替换数组（已知的整数组替换），于是编辑器被关闭、**未保存的 `draft` 被丢弃**；`openEntry`（约 `:121`）点另一个文件时也直接覆盖 `draft` 和 `savedText`，**没有脏检查**，也没有 try/catch，读错误会变成未处理的 rejection。应改为按 `skill.id` 监听，切换文件前确认。
5. **`AgentDetailView.vue` 同样的草稿被覆盖（中）[已核对]**：`watch(agent, v => Object.assign(draft, {...}))` 每当智能体对象变化就重置整个草稿；`toggleResource` 的注释说它避免覆盖其它区段的未保存草稿，但 `store.saveAgent` 会替换智能体对象，watcher 随后就用已保存的值覆盖未保存的名称、描述、指令；`watch(locale)` 和 `refreshAgentsAndSquads()` 也触发同样的重置；离开路由时没有未保存守卫。`SquadDetailView.vue` 有同样的 `watch(squad)` 重置。
6. **设置页最后一次修改会丢（中）[已核对]**：`SettingsView.vue` 的 `onBeforeUnmount(() => window.clearTimeout(saveTimer))` 丢掉了挂起的 300ms 防抖保存而不是 flush；设置页被 keep-alive，但应用关闭或被淘汰（超过 `:max=24`）时同样丢；每次按键的保存还会写入写到一半的值（`webhookPort`、`updateProxy`（每次按键都通过 `setUpdateProxy` 实时生效）、`genApiUrl`、`genApiKey`）；`v-model.number` 对空输入得到 `""`，`runTimeoutMinutes` 和 `webhookPort` 会被存成 `String("")`，保存前没有任何校验；每次保存后 `watch(store.data.settings)` 又用裁剪后的已保存值重新填充表单，在提示词文本框里打尾部空格或快速编辑可能被这次往返覆盖。
7. **Esc 会丢掉表单里未保存的输入（中）[已核对]**：`TaskCreateDialog.vue:~160`、`CreateSkillDialog.vue:~66` 注册文档级 `Escape` 处理器，直接 emit 关闭，没有脏检查；`CreateRuntimeDialog.vue:52` 同样，会丢掉用户输入的 API 网关配置；它在 Esc 本来是用来关闭已打开的 `UiSelect` 或建议菜单时也会触发。（`UiModal` 的 `@click.self` 到处都是空操作，因为 `UiModal` 在没设 `closeOnBackdrop` 时会剥掉 `onClick`，所以点击背景不是风险。）

### 14.2 卡顿 / 内存 / 监听器泄漏

1. **大纲计算是二次方的（高）[已核对]**：`editor/outline.ts` 对每个条目调用 `symbolEndLine` → `codeEndLine` / `headingEndLine`，而它们每次都对**整个文件** `content.split(/\r?\n/)`，所以是 条目数 × 行数 次分配；`jsonOutline`、`yamlOutline` 每个顶层键一项；`activeOutline`（`WorkspaceWorkbench.vue:722`）没有大小保护，每次按键因 `file.content` 变化而重算，`syncEditorDocument` 也被 `activeFile.content` 的 watcher 触发。5 万行的 JSON、lock 文件或有数千符号的文件会让打字冻结数秒。（§4.1 已列，这里补上具体机制和修法：只 split 一次、对文件大小设上限、加防抖。）
2. **被 keep-alive 缓存的工作台仍保留全局捕获阶段的按键处理器（高）[已核对]**：`WorkspaceWorkbench.vue:4713-4715` 只在 `onMounted` 里往 `window` 注册 `handleWorkbenchShortcuts`（捕获阶段）、`handleEditorTabKeys`、`handleAddToChatKey`，移除在 `onBeforeUnmount`。应用最多保活 24 个页面，`ProjectWorkspaceView` 是每个项目路径一个实例，所以**被隐藏的项目工作台仍在处理快捷键**：Ctrl+Shift+\` 在每个保活工作台里调用 `createTerminal()`，没有活动状态守卫，会**在隐藏的工作台里创建隐藏的终端 / PTY**；Ctrl+P、Ctrl+Shift+E、Alt+Shift+F 也在隐藏实例里运行并 `preventDefault` / `stopPropagation`。需要用 `onActivated` / `onDeactivated` 门控（该文件里 `onActivated` 目前只用于标题栏，`:472`）。隐藏期间 `writeLockTimer`（10 秒 `setInterval`，`:2389`，我加的）也不会暂停，`ResizeObserver` 也还挂着。
3. **单例注册表被多个工作台互相覆盖（中）[已核对]**：`unsaved-editor.ts` 的 `registerUnsavedLeaveHandler`、`registerUnsavedDirtyChecker`、`registerDirtyEditorPaths` 是模块级单例，最后挂载的工作台胜出，任何工作台的 `onBeforeUnmount` 都把它们设成 null。同时打开两个项目时，卸载或被 LRU 淘汰其中一个，就会让另一个的脏检查失效，应用关闭、路由切换、回滚都不再提示。`codeIndex.setPaused(running)`（我加的）也有同样的“最后写入者胜”问题：一个空闲的隐藏工作台的 watcher 可能在另一个项目运行期间重新开启索引。
4. **每个工作台实例各一份 `runStates` 监听器（中）[已核对]**：约 4936、4973 行以及另一处，形如 `Object.values(store.runStates).filter(... store.data?.sessions.find(...)).map(...).join("|")`，每个工作台实例在每个流式事件上都跑一遍，复杂度 运行数 × 会话数；最多保留 24 个工作台会成倍放大。
5. **关闭标签后 Monaco 模型从不 dispose（中）[推断]**：`EditorWithDiff` 用 `<VueMonacoEditor :path=...>`，库按路径保留一个模型，我没找到标签关闭时的 `model.dispose()`；每个标签还持有 `file.content`、`original` 和 Monaco 模型；媒体标签保留完整的 `file.content` 字符串，媒体 `:src="activeFile.content"`（假定是 data / base64 内容）。
6. **本地历史在每次保存和查看时整体读取并解析（中）[已核对]**：`readStored()` 对整个 blob（数 MB）`JSON.parse`，在 `listLocalHistory`、`recordLocalHistory`、`localHistoryEntry`、时间线 `rows` 计算属性的每次 `historyTick` 里都会跑，保存时再整体 `JSON.stringify`，每次 Ctrl+S 都是同步的主线程开销。
7. **MCP 后台刷新（中）[部分为推断]**：`McpView.vue:~375` 的 `watch(servers, rows => mcpTools.refreshInBackground(rows))` 在每次资源数组被替换时触发（已知的整数组替换），调用 `schedule_mcp_tools_refresh`，后端大概会为每个启用的 stdio 服务器起进程；`stores/mcp-tools.ts` 的 `applyEntry` 每个事件克隆整个 `probes` 映射（含日志）和 `loadingIds`，对 n 个服务器是 O(n²)。
8. **小项（低）**：`onWorkbenchDragOver` 在每个 dragover tick 都跑 `elementFromPoint` 和 `treeItemFromPoint`；`UiSelect`（多选）在每次值变化时重新绑定 `ResizeObserver`（计算数组每次是新引用）；`AutomationView` 每行每次渲染两次 `projects.find`。

### 14.3 安全

1. **远程目录条目一键安装（中）[推断]**：`CatalogBrowse.vue` 直接 emit `install`；`McpView.installCatalog` 调 `store.installMcp(item.name, item.install, owner)` 没有确认；`SkillsView.installCatalog` 调 `importSkillFromUrl(item.install)`；`CreateSkillDialog.installCatalog` 是 `form.url = item.install; submitUrl()`。数据来自远程目录，一个恶意或被攻陷的条目会变成配置好的 stdio MCP 命令或导入的技能指令；配合 14.2 第 7 条，已启用的 MCP 还会被自动探测（也就是被启动）。建议显示命令或 URL 并要求确认，目录安装默认为禁用。
2. **渠道消息里的隐藏指令（中）[推断]**：`parseUserPromptNodes` 会从可见文本里移除 `ASSIGNMENT_PATTERN`（`[指派要求]\n- ...`）；来自外部发送者的渠道消息（`sourceType` 为 feishu / lark，由 `ChatMessageItem` 渲染）走同一个解析器；发送者可以嵌入界面隐藏但智能体能在原始内容里看到的 `[指派要求]` 或 `[实体引用]` 块，这是对提示词注入的隐藏；用户键入的含这些标记的文本同样会被隐藏或变成芯片。
3. **密钥处理（低~中）**：`SettingsView.vue` 的 `genApiKey` 整个会话以明文保存在 `form` 和 `store.data.settings` 里，每次防抖按键保存都写进通用的 `saveSettings` 字符串映射（不进 `localStorage`，不进日志，输入框是密码框）；`CreateRuntimeDialog.applyLoaded` 把完整明文 `current.apiKey` 加载进 WebView 状态（`initialApiKey`），还有可能含密钥值的环境变量文本；`ChannelsView` 对 `appSecret` 的处理是对的（只写、留空表示不变）；`AutomationView.webhookUrl` 把承载令牌明文显示在 `<code>` 和 `:title` 里；`McpView` 的密钥（`headersText`、`envText`）是普通文本框，不遮挡（设计如此，但可见）。
4. **本地历史把文件内容明文存进 `localStorage`（中）[已核对]**：`multara.localHistory` 每个文件最多保留 20 个版本、每个 200KB，**不排除 `.env` 和密钥文件**，无限期保留，工作区被移除时也不清理。
5. **开发模式的 `eval` 桥（低）[已核对]**：`e2e/devBridge.ts:221` 的 `eval(payload.js)` 由对 `/__e2e/next` 的轮询驱动，只在 `import.meta.env.DEV` 下导入（`main.ts:28`），但任何能访问开发服务器的本机进程都能在开发构建里获得带 Tauri IPC 的代码执行。
6. **这一路没有发现新的 XSS**：`v-html` 只在 `RichContent` 和 `MarkdownPreview` 里（已审或已知）；`openExternalUrl` 强制 `^https?://`，静态的“了解更多”链接都走它；`MediaPreview` 把 `:src` 绑到文件内容，后端生成 data URL 时是安全的，但没有核对。

### 14.4 对之前内容的补充

- §6.1（`keep-alive` 缓存最多 24 个页面）当时我只写了“被缓存页面仍在响应式更新、定时器不会停”。这一轮发现更直接的后果：**被缓存的工作台还会响应全局键盘快捷键，包括在隐藏的工作台里创建终端**（14.2 第 2 条）。建议它的优先级高于其它 keep-alive 相关的问题。
