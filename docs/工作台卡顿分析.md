# 工作台卡顿分析：长对话后聊天、编辑器、整个窗口卡死

现象（用户报告）：

1. Multara 回答很久之后，整个工作台卡死。
2. 聊天里出现大量 `Tool>`（空名字工具行）。
3. 点开文件，先出现一行代码，再变成多行。
4. 编辑器里光标不见了；点了哪一行，哪一行的文字就看不见。

这份文档只做分析，没有改代码。结论分三类标注可信度：

- **已证实**：有本机数据库 / 日志 / 代码三方面证据。
- **代码可推断**：代码里能看出机制，但没在真机上复现。
- **待验证**：只是合理假设，文末给了验证办法。

对照项目：编辑器参考 `../vscode`，聊天参考 `../vscode` 和 `../multica`。

## 0. 一句话结论

**直接诱因（已证实）**：一次运行产生了 12,000+ 条时间线事件，其中 6,110 条是**空名字的 `tool_use`**，每条都配一条报错的 `tool_result`。前端对每条事件都渲染一个 DOM 行，所以出现成百上千个 `Tool>`。

**放大器（已证实 / 代码可推断）**：聊天链路没有任何“量级保护”——每个流式片段都全量重算、全量写库、全量序列化、全量重渲染，消息列表没有虚拟化，`runStates` 永不清理。事件一多，主线程就被占满，编辑器（同一个 JS 线程）一起卡死。

**编辑器症状**：和聊天卡顿共用主线程；另外有几处独立的编辑器问题（只读锁、按键级全文 diff、每次重建 view zone、每次移动光标都跑 git blame）。其中“光标消失”最可能是只读锁，“点哪行哪行字消失”目前只有候选，需要 DevTools 确认。

```
seq 2  tool_use  Bash  call_P0yARJ…   input {}
seq 3  tool_result      call_P0yARJ…   <tool_use_error>InputValidationError: Bash failed …
seq 4  tool_use  (空)  call_P0yARJ…   input {"__unparsedToolInput":{"len":2,"raw":"{\""}}
```

也就是：同一个 `call_id` 下，**工具参数 JSON 被切成一个个碎片，每个碎片都变成了一个独立的 tool_use**。模型收到报错后继续乱发，形成死循环（6,000 多轮）。

### 1.2 这些碎片很可能来自网关代理（代码可推断）

这个 run 走的是自定义 runtime，经过 `src-tauri/src/gateway_proxy/streaming.rs`。Chat 格式的增量解析：

```rust
// streaming.rs  extract_delta, ApiFormat::Chat
tool_start: tool.get("id").is_some(),
```

```rust
// streaming.rs  emit
if delta.tool_start {
    self.emit_tool_start(&delta.tool_id, &delta.tool_name);   // 无条件开一个新 tool_use block
}
```

只要某个上游在**每个 delta 片段里都重复带 `id`**（一些 OpenAI 兼容服务商确实这样做），代理就会为每个参数碎片都发一次 `content_block_start`，下游 Claude CLI 看到的就是一串空名字、参数残缺的 tool_use，正好吻合上面的 `__unparsedToolInput`。同一函数还只读 `tool_calls/0`，并行工具调用（`index>0`）会被丢掉。

> 状态：机制吻合，但**没有抓到上游原始报文**，不能 100% 断定。验证办法见 §6。

### 1.3 前端把这些空工具原样渲染成 `Tool>` 行（已证实）

- `ToolCallRow.vue`：`name = inferToolName(item) || "Tool"`，空名字就显示成 `Tool …`。
- `timeline-display.ts` 的 `isBlankTool` 要求 `Object.keys(resolvedInput(item)).length === 0` 才算空；而这些碎片的 input 是 `{"__unparsedToolInput":…}`，**key 数为 1，不被判空**，所以全部渲染。
- 每个 `tool_use` 又配一个报错 `tool_result`，没有任何合并 / 折叠 / 上限。

### 1.4 后端日志：旧版本有严重的数据库锁等待（已证实，但多数已修）

`multara.log.old`（2026-10-22 ~ 10-29，旧版本）：

- `WAIT/GOT db` 共 3,700+ 条，等锁**最长 84.9 秒**。
  - `executor.rs:2032`：688 次，累计 3,653 秒；
  - `executor.rs:740`（`dispatch_pending`）：278 次，累计 1,774 秒；
  - 其余在 `automation.rs`、`commands.rs`、`conversation.rs`。
- 主线程（线程 `[1]`）上同步执行的 `bootstrap` 共 2,908 次、累计 3,780 秒，单次最长 22.8 秒。10-23 ~ 10-24 期间几乎每 1.4 秒一次。

当前 `multara.log`（10-29 09:26 之后）：

- 数据库等锁只有 2 条（一次 2.0 秒，在 `executor.rs:2047`）。
- 主线程上 `list_chat_messages` 12 次共 0.2 秒、`read_workspace_file` 150 次共 0.1 秒，都很快。
- `bootstrap` 已是 `async + spawn_blocking`，不再占主线程。

**判断**：后端锁竞争在近期版本已大幅缓解，当前这轮卡死主要是**前端主线程**问题。但 `executor.rs` 的“每条事件拿一次全局数据库锁”结构没变（见 §2.2），遇到 12,000 事件的 run 仍会被放大。

### 1.5 `multara.log` 里没有前端卡死的记录

Rust 日志只能看到后端。前端主线程卡死不会出现在这里，所以下面前端部分的“慢”是靠代码和复杂度推断的，需要 §6 的性能录制来量化。

## 2. 聊天链路：每个流式片段都做了什么

一个 token 片段的完整路径：

```
CLI stdout 一行
 → executor.rs: persist_from_line / normalize_runtime_line
 → merge_timeline_item（整段拼接）
 → persist_timeline_item（整段 upsert 进 SQLite）
 → app.emit("run-event", 含整段合并后的内容)
 → [IPC 序列化 / 反序列化]
 → app.ts listen 回调
 → messages.value[sid] = [...sessionMessages]   （整数组换新引用）
 → ChatPanel displayMessages 重建（每条消息 {...message} 浅拷贝）
 → 每个 ChatMessageItem / AssistantMessage 重算
 → RichContent 整段 marked + DOMPurify + innerHTML + hljs
 → watch → nextTick → scrollTo("smooth")
```

### 2.1 后端：整段合并、整段写库、整段发送（已证实，代码）

`executor.rs`：

- `should_merge_timeline`：连续的 `text` / `thinking` 合并成一个 item。
- `merge_timeline_item`：`format!("{}{}", previous.content, item.content)`，**每次新建整段字符串**，还对整段做一次 `serde_json::from_str`。
- `persist_timeline_item`：`INSERT … ON CONFLICT DO UPDATE SET content=…`，**每个片段把累计全文再写一遍**。
- `outgoing.timeline_item = Some(item)`：事件里带的是**累计全文**，同时 `outgoing.chunk` 又带增量。

结果：长度 n 的回答，总写库量和总 IPC 量是 **O(n²)**，而且前端同一段文字存了两份（`message.content` 拼接 + `timeline[].content` 全量覆盖）。

每次写库都要 `lock_db()` 拿全局 `Mutex<Connection>`，和 `dispatch_pending`、`automation_tick`（每 2 秒）、`list_chat_messages`、diff 读写抢同一把锁。

`maybe_capture_file_snapshot` 在每个 `tool_use` 上拿锁、读磁盘、写 `turn_file_snapshots`，并把**整个文件内容**通过事件发给前端（`snapshotContent`）。

### 2.2 前端事件处理：每片段 O(n) 工作（已证实，代码）

`stores/app.ts` 的 `run-event` 回调：

| 行为 | 代价 |
|---|---|
| `sessionMessages.find(id)` | O(消息数) |
| `timeline.findIndex(seq)` + `timeline.sort(...)` | O(timeline) ，timeline 上万时每次都全排序 |
| `messages.value[sid] = [...sessionMessages]` | 整个数组换新引用，**所有依赖者重算** |
| `existing.content = applyAssistantChunk(...)` | 字符串拼接，同时 timeline 里还有一份全文 |
| 状态变化时 `refreshTaskInboxSurfaces()` | 拉全量 tasks/sessions/inbox |
| 结束时 `backend.listChatMessages(sid)` | **整个会话所有消息 + 所有 timeline**（N+1 查询，见 `commands.rs`），整体替换 `messages.value[sid]` |

另外：

- **`runStates` 永不清理**（`app.ts` 没有任何 `delete runStates[...]`）。每次 run 都往里加一项，而 `ChatPanel`、`WorkspaceWorkbench`、`TaskActivity`、`project-home` 等 8 处在每次事件时都 `Object.values(store.runStates)` 遍历。运行越久、历史越多越慢。
- 完成后 `useDiffStore().loadActive()` 会把所有活动快照的**完整文件内容**再读一遍，整体替换 `snapshots / turnOrder / chunkStates`。

### 2.3 消息列表：没有虚拟化，且每片段全员重渲染（已证实，代码）

`ChatPanel.vue`：

```ts
const displayMessages = computed(() => {
  for (const message of sessionMessages.value) {
    ...
    result.push({ ...message, duplicateCount: 1 });   // 每次都新建对象
  }
});
```

- `sessionMessages` 每个片段都是新数组 → `displayMessages` 重算 → **每条消息都是新对象** → 所有 `ChatMessageItem` 的 `message` prop 变化 → 全部重新渲染，而不仅是正在流式的那条。
- `ChatMessageItem.vue` 对**每条消息**调用 `speakerForMessage(..., { messages: sessionMessages })`、`sentTargetForMessage`；`message-speaker.ts` 里 `resolveTurnTarget` 做 `messages.findIndex` + `messages.slice(0, index)`。N 条消息 × O(N) = **每片段 O(N²)**。
- `AssistantMessage.vue` 每条消息都算 `liveAssistantText(timeline)`、`extractQuestions`、`isLeaderAssignment`（又读全量 `store.messages`）。
- `messageGroups` / `currentTurnAssistant` / `questionStates` / `workingLines` 等 computed 每片段也都重算。
- 列表是普通 `v-for`，**没有虚拟滚动**，CSS 里也没有 `content-visibility` / `contain`（`styles.css` 12,223 行，0 处）。

### 2.4 时间线渲染：每个工具一行 DOM，且几处 O(n²)（已证实，代码）

- `ProcessFold.vue` 的折叠态是 `<details>`，**子内容照常渲染**，只是被浏览器折叠。历史消息里的数千个 `ToolCallRow` 全在 DOM 里。
- `groupTimeline`（`timeline-display.ts`）里 `results.find(...)` 放在 `for (const item of top)` 循环内 → **O(n²)**；12,000 条事件就是上亿次比较，且运行中每个事件都重跑。`coalesceTimeline` 也每次全量重算。
- `ToolCallRow` 展开时 `JSON.stringify(item.input, null, 2)`；`shellTranscript`、`shellResultText` 里有 `JSON.parse`，每个工具一份。
- `FileDiffCard.vue`：每张卡都 `watch(reviewFile)` 读磁盘、监听 `diffStore.diskEpoch` 再读磁盘，`reviewFile` 还遍历 `diffStore.baselines` 所有 key。有 50 张编辑卡，`diskEpoch` 变一次就是 50 次 `readWorkspaceFile` + 50 次 `lineDiff`（`lineDiff` 是 O(n·m) 的 DP，阈值 80,000 格）。

### 2.5 Markdown：每个片段整段重解析（已证实，代码）

`RichContent.vue`：

```ts
const html = computed(() => DOMPurify.sanitize(marked.parse(props.content), ...));
// <div v-html="html"> + watch(html, enhanceBlocks)
```

- 正文每长一点，`marked` 重新解析**整段**，`DOMPurify` 重新清洗**整段**，`v-html` 重建**整个 DOM**。
- 重建后 `enhanceBlocks` 对**所有**代码块重新 `hljs.highlightElement`、重新包装按钮、重新做 `TreeWalker` 找路径、重新绑定链接监听。
- 对 `mermaid` 代码块，流式期间每次片段都会尝试渲染，半截图表会走 `catch` 分支，且 `mermaid` 是动态导入后的重量级渲染。
- 同一条消息的 O(n²)：正文越长、代码块越多越糟。

### 2.6 自动滚动：每个片段触发一次 `smooth` 滚动（代码可推断）

`ChatPanel.vue` 的 watch 监听 `at(-1).content`、`timeline.length`、`messages.length`，每次都 `await nextTick()` 然后 `scrollToBottom("smooth")`。`smooth` 滚动被每个片段重启；`handleScroll` 里 `listIsAtBottom` 用 `getBoundingClientRect()`，在滚动动画期间不断触发强制布局。内容在长高时，`followBottom` 还可能被误判为离开底部，出现“回到底部”按钮闪烁和抖动。

### 2.7 其它持续开销（代码可推断，影响较小）

- `liveTimer`：运行期间每秒 `liveClock` 更新一次，驱动 `workingLines` / `liveAnchor` 重算。
- `filesBeingWritten`（`WorkspaceWorkbench.vue`）：每个片段遍历所有 running run 的整条 timeline。
- `WorkspaceWorkbench.vue` 里有两个 `watch(() => Object.values(store.runStates).filter(...).map(...).join("|"))`，每个事件都遍历 `runStates` 并对每项 `sessions.find`。
- `stores/running-terminals.ts` 有轮询定时器。

## 3. 编辑器链路

编辑器与聊天**共用渲染进程的主线程**。第 2 节任何一个长任务（几百毫秒的 JS）都会让 Monaco 无法绘制光标、响应点击、完成布局——这解释了“点了没反应”“先出现一行再变多行”这类**渲染被延迟**的症状。除此之外，编辑器自身还有下面这些问题。

### 3.1 按键级全文 diff，且同步跑在主线程（已证实，代码）

`EditorWithDiff.vue`：

```ts
editor.onDidChangeModelContent(() => {
  ...
  refreshDiff(current);        // 每次按键
  gutterRef.value?.schedule(); // 120ms 防抖
});
```

`refreshDiff` → `diffStore.getChunksForFile` → `computeLineDiff` → `diff` 库的 `structuredPatch`（`utils/diff-engine.ts`），**同步**、**无防抖**、**无耗时上限**，对**每一个 baseline**（每个 turn 一份）各跑一遍整文件 diff。大文件 + 多轮 AI 修改，每按一次键就是 K 次全文 diff。

`GitGutter.paint()` 里 `editor.getValue()` + `gitGutterModel(...)` 也是整文件，每次内容变化 120ms 后再来一遍。

对照 VSCode：`quickDiffModel.ts` 用 `ThrottledDelayer(200)`，diff 在 worker 里算，并有 `maxComputationTimeMs: 1000` 上限。

### 3.2 每次刷新都销毁并重建所有 diff 覆盖层（已证实，代码）

`DiffOverlayManager.applyChunks`：每次调用 `clearAll()`（删装饰、删 view zone、删 overlay widget），再重建所有 view zone（每个含 `colorize` 异步着色）、overlay widget、按钮 DOM，再 `deltaDecorations`。即使 chunk 内容完全没变也这样做。

`changeViewZones` 会触发 Monaco 重新布局。配合 3.1 的按键级调用，**每次按键 / 每次 store 变化都在拆装 DOM**，是光标闪烁、行内容重绘异常的高概率来源。

### 3.3 深度监听整个 diff store（已证实，代码）

```ts
watch(() => [diffStore.chunkStates, diffStore.baselines],
  () => refreshDiff(editor.getValue()),
  { deep: true });
```

`baselines` 是 `Map<key, 整文件内容>`，`deep: true` 会遍历所有内容字符串依赖。聊天侧每收到一个 `file_snapshot`、每次 `loadActive()` 整体替换，都会触发编辑器重算 diff。另一个 watch 还在 getter 里做 `[...snapshots.keys()].join("|")`、`[...turnOrder.values()].map(...)`，每次 store 改动都重新拼字符串。

### 3.4 `refreshDiff` 触发太多源头（已证实，代码）

`refreshDiff` 同时被：按键、模型切换、`chunkStates/baselines` 深监听、`diskEpoch` 变化、`isRunning` 变化、`props.content` / `snapshots` / `turnOrder` 变化触发，没有合并。一次 AI 写文件结束，会连续触发好几次，每次都是 §3.1 + §3.2 的全套。

### 3.5 “写入中”只读锁（代码可推断，最可能解释“光标不见了”）

```ts
// EditorWithDiff.vue
readOnly: Boolean(props.readOnly || props.writing),
// WorkspaceWorkbench.vue
:writing="activeFileBeingWritten"
```

`filesBeingWritten` 的规则：该 run 状态为 `running`，且 timeline 里存在 `Edit/Write/Create` 的 `tool_use` 还没有配对的 `tool_result`。

Monaco 在 `readOnly` 时**不显示光标**，也不能输入。以下任一情况都会让当前文件被锁住：

1. 一个 run 一直不结束（如 §1.1 的 run，到现在仍是 `running`）。
2. 某个写文件的 `tool_use` 因为 `callId` 缺失 / 不一致（`"__anon__"` 兜底）而一直没被配对。
3. `runStates` 里残留了 `running` 状态（永不清理 + 异常结束时没收到终止事件）。

这三条都和“回答久了之后光标没了”高度吻合。同时“保留 / 撤销”按钮也会因为 `activeFileBeingWritten` 被禁用。

### 3.6 光标移动即触发 git blame 子进程（已证实，代码）

`git-blame-editor.ts`：

```ts
editor.onDidChangeCursorPosition(() => this.schedule());   // 180ms 防抖
...
blame = await backend.gitBlameLine(workspaceId, filePath, position.lineNumber);
```

每换一行就起一次 `git blame -L`（日志里 `git_blame_line` 已有记录），完成后：

- 改写一个全局 `<style>` 元素里的 `::after { content: "..." }` 规则（触发整页样式重算）；
- 用 `afterContentClassName` 在当前行末尾加一个内联装饰（`createDecorationsCollection().set`）。

这会让**当前点击的那一行**的渲染节点被 Monaco 重建。结合 `.git-blame-after::after { margin-left: 50px; … }`，它是“点了哪行，哪行文字异常”的**第一候选**，但没有在真机上复现，属于待验证。

### 3.7 打开文件时的两段式显示（代码可推断，待验证）

`openEditorFile` 的顺序：`readWorkspaceFile` → `adoptEditorModel`（对已存在模型 `setValue`）→ 改 `editorTabs` / `activateEditorTab` → `nextTick` → `reveal`。同时：

- `VueMonacoEditor` 按 `:path` 取 / 建模型；`codeIndex`（`editor/code-index.ts`）可能已为同一文件建过索引模型；
- `EditorWithDiff` 的 `watch([filePath, workspaceId, diskEpoch])` 又会 `replaceEditorValue` 一次 `setValue`；
- `onEditorMount` 里 `refreshDiff` + `GitGutter.schedule` + `GitBlame` 构造时立刻 `schedule`；
- `automaticLayout: true` 靠 `ResizeObserver` 在容器尺寸稳定后才第一次完整布局，而 `.editor-main > .monaco-host` 是绝对定位 + `v-show`，初始阶段容器高度可能先是 1 行高。

当主线程被聊天占满时，“模型建好但布局未完成”的中间帧会被用户看到：**先一行，再展开**。具体是 CSS 链路问题还是 `setValue` 时序问题，需要 §6 的验证。

### 3.7.1 工作区索引在后台大量建模（已证实，代码）

`code-index.ts` 会为工作区最多 **3,000 个源文件 / 32MB** 建 Monaco 模型，`monaco-workspace.ts` 又 `setEagerModelSync(true)`，所有模型都同步给 TS worker。每次磁盘变化（AI 写文件结束触发的 `diskChangeRefreshScheduler`）都会 `collectSourceFiles` 并对变更文件 `model.setValue`。主线程要为这些模型做创建、同步和 marker 清理（`monaco.ts` 的 `onDidChangeMarkers` 对每个 URI `maybeClear`）。AI 密集改文件的时候，这块是持续的后台负载。

### 3.8 其它编辑器侧小项（代码可推断）

- `editorOptions` 是 computed，每次返回新对象，`VueMonacoEditor` 会对 `options` 做一次 `updateOptions`；
- `editor.onDidChangeCursorPosition(() => syncEditorDocument())` 每次光标移动都写一次 `editorStatus` store；
- `pendingDiffFiles` computed 同时依赖 `diskEpoch / chunkStates / baselines / snapshots / turnOrder`，并对每个待审文件算一遍 diff。

## 4. 因果链：为什么是“回答久了之后才卡”

```
上游把一个工具调用的参数切成碎片，每个碎片都带 id
  → 网关 emit_tool_start 每次都开新 tool_use（空名字 + 残缺 JSON）
  → CLI 报 InputValidationError，模型继续乱发，无任何熔断
  → run 事件数十分钟内涨到 12,000+
        │
        ├─ 后端：每事件 1 次拿全局 DB 锁 + upsert + IPC 序列化
        ├─ 前端 store：每事件 sort timeline、换新消息数组、遍历不断增长的 runStates
        ├─ 聊天 UI：每事件全员重渲染；groupTimeline O(n²)；数千个 <details> 行常驻 DOM
        └─ 编辑器：被动接收 store 变化 → 深监听 → 全文 diff → 重建覆盖层；
                    run 仍是 running → 文件被锁为只读 → 光标消失
  → 主线程长任务累积 → 点击无响应、布局延迟（先一行后多行）、整个窗口像卡死
```

所以“回答久了”并不是时间本身，而是**事件数 / 时间线长度 / 消息总量**一直在涨，而每个环节的单次代价都至少是 O(n)，几处是 O(n²)。

## 6. 修复方案（按收益 / 风险排序）

### P0：先止血

1. **网关代理：碎片不能开新 tool_use。** `streaming.rs` 的 `ApiFormat::Chat`：
   - 以 `tool_calls[i].index` 作为工具身份，而不是 `id.is_some()`；
   - 同一个 `index` 且 `id` 相同或为空时，只追加 `arguments`，不再 `emit_tool_start`；
   - 遍历 `tool_calls` 全部元素，不只读 `/0`；
   - 补测试：同一 `id` 连续 N 个 delta 只产生 1 个 `content_block_start`。
2. **后端熔断。** 同一 run 里连续 N（如 20）次 `tool_result` 带 `<tool_use_error>` 或空 `tool_use`，直接停止并以失败结束，写明原因。同时丢弃 `tool` 为空且 input 只有 `__unparsedToolInput` 的事件，不入库、不发前端。
3. **前端过滤。** `isBlankTool` 把 “input 只含 `__unparsedToolInput`” 视为空；对同 `callId` 的连续报错 `tool_result` 折叠成一行 “×N”。
4. **清理现场。** 现在那个 run 还在 `running`，手动停止它；`runStates` 在 run 终止后延迟清除（保留最近 N 项）。

### P1：把每片段的代价降到常数级

5. **事件节流。** 后端把 `text/thinking` 的 `run-event` 合并，每 50~100ms 发一次，且 **只发增量**，不再带累计全文（前端自己拼）。
6. **后端写库去 O(n²)。** 流式期间 `text/thinking` 先在内存累积，按时间（如 500ms）或事件结束 / 工具切换时落库；不要每片段 upsert 全文。
7. **前端 store。** 事件先进一个队列，用 `requestAnimationFrame` 批量应用；timeline 用 `Map<seq, item>` + 追加（seq 本就单调，不要每次 `sort`）；不要 `[...sessionMessages]`，直接改 reactive 元素；`messages` 改用 `shallowRef` + 手动触发。
8. **聊天列表。**
   - `displayMessages` 不再 `{...message}` 拷贝，`duplicateCount` 另存 Map；
   - `ChatMessageItem` 的 speaker / target 提到 `ChatPanel` 一次性算成 Map（O(N)），不要每条消息里各算一遍；
   - 引入虚拟滚动（可用 `vue-virtual-scroller` 或自写窗口化），至少对已完成的历史消息；
   - 折叠态 `ProcessFold` 用 `v-if` 真正不渲染子节点，展开时再渲染；
   - `groupTimeline` 先按 `callId` 建 `Map` 再配对，去掉 `results.find`；
   - 已完成消息的 timeline 分组结果缓存。
9. **Markdown。** 流式期间只重渲染最后一个未闭合的 block（按空行 / 代码围栏切块，已完成的块缓存 HTML 且不再 `enhanceBlocks`）；hljs / mermaid 只在块闭合后处理；参考 VSCode 的渐进渲染速率。
10. **滚动。** 流式期间用 rAF 合并，且用 `behavior: "auto"`，只在用户确实在底部时执行；`listIsAtBottom` 缓存或用 `IntersectionObserver` 哨兵代替 `getBoundingClientRect`。
11. **`listChatMessages` 改增量。** 结束后只拉该 run 对应的消息，或按 `since` 拉；timeline 懒加载（展开时再取）；同时修掉 N+1 查询。
12. **`FileDiffCard`。** 不要每张卡各自读盘：统一在 diff store 里按文件缓存一份 live content，`diskEpoch` 变化时批量刷新，且只刷新可见卡片。

### P1：编辑器

13. **diff 去抖 + 上限。** `refreshDiff` 用 200ms `ThrottledDelayer`；计算放到 Web Worker（或至少 `maxComputationTime`，超时则降级为仅标记“有改动”）；对多个 baseline 只算与当前文件相关的最新两份。
14. **覆盖层增量更新。** `DiffOverlayManager.applyChunks` 先对比 `chunkId + hunk` 签名，没变就不拆装；变了只增删差异项。
15. **去掉深监听。** `watch(..., { deep: true })` 改成 store 暴露的 `version` 计数器，变更时 `+1`；`pendingDiffFiles` 等依赖同样改用版本号。
16. **只读锁更准。** `filesBeingWritten` 只统计**该 run 仍在运行、且最近 N 秒内有事件**的写入；run 终止（含异常）或 tool_use 超时（如 30 秒无结果）就解锁；`readOnly` 状态在编辑器里显示一条明确提示，而不是静默吞掉光标。
17. **blame 缓存。** 参考 VSCode：打开文件时一次性拿整文件 blame 并缓存，光标移动只查表；去掉对全局 `<style>` 的反复改写，改用按提交缓存的固定 class；或至少在编辑器失焦、内容 dirty 时暂停。
18. **索引节流。** `code-index` 在 AI run 运行期间暂停 `refreshAll`，run 结束后一次性刷新；降低默认 `MAX_INDEXED_SOURCE_FILES`；考虑关闭 `setEagerModelSync` 或仅对打开的文件同步。
19. **打开文件两段式。** 用 `v-if` + 固定高度容器，保证 `VueMonacoEditor` 挂载时容器已有尺寸；打开文件时去掉重复的 `setValue`（`adoptEditorModel` 与 `replaceEditorValue` 二选一）；初次 `refreshDiff` / `blame` / `gutter` 推迟到 `requestIdleCallback`。

### P2：观测与防护

20. **性能埋点。** `run-event` 回调耗时、每帧长任务（`PerformanceObserver` `longtask`）、timeline 长度超过阈值时在界面提示；日志里补前端长任务记录，写进 `multara.log`。
21. **量级保护。** 单个 run 的 timeline 超过 2,000 条时自动折叠到摘要、停止实时渲染；单会话消息过多时分页。

### 7.1 确认 §1.2（碎片来源）

1. 给 `gateway_proxy` 的 Chat 流加一个调试开关，把上游每个 SSE `data:` 原样写到 `multara.log`；

1. 开发模式（`pnpm tauri:dev`）里打开 WebView DevTools → Performance，录制一次长回答（建议复用现在的 run 数据）；
2. 看 Main 线程的火焰图，重点找：`run-event` listener、`groupTimeline`、`marked.parse`、`hljs.highlightElement`、`computeLineDiff / structuredPatch`、`changeViewZones`；

### 7.3 确认“光标不见”和“点哪行哪行字不见”

光标不见：

1. 复现时在控制台执行 `monaco.editor.getEditors()[0].getOption(monaco.editor.EditorOption.readOnly)`；
2. 为 `true` 就是 §3.5 的只读锁；再看 `store.runStates` 里有无 `status === "running"` 且超过一小时的项。

点行后文字消失：

1. 复现后用元素检查器看该行 `.view-line` 的子节点，是否有 `.git-blame-after`、`.diff-line-added`、`.diff-removed-zone`、`.sticky-widget` 覆盖；
2. 临时在控制台关掉 blame（卸掉 `GitBlame`）/ 关掉 `stickyScroll` / 清掉 `DiffOverlayManager`，逐项确认；
3. 看该行 DOM 是否被反复重建（Elements 面板里节点闪动）。

两段式显示：Performance 面板里对比 “模型创建 / `setValue` / 第一次 layout” 的时间点，确认是主线程被占还是布局顺序问题。
