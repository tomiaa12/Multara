# 运行时添加与识别方案

## 1. 结论

1. **参考实现 选了带图标的运行时之后只有「名称 / 命令 / 描述」，是对的设计。** 选内置 CLI 时，它只是"换个命令名、加几个固定参数"来启动同一种 CLI。API 地址、Key、模型这些都交给 CLI 自己的配置（`~/.claude/settings.json`、`~/.codex/config.toml`、cc-switch 等），参考实现 不接管。
2. **Multara 现在把「API 协议 / Base URL / Key / 模型 / 环境变量」塞进了每一种运行时的表单**，所以选 Claude 也要面对一堆网关字段，而且对 Cursor、Copilot 这类根本不支持自定义网关的 CLI 也显示了这些字段（填了也没用）。
3. **改法：拆成两种添加方式。**
   - 「基于内置运行时」：和 参考实现 一样，只有名称、命令行、描述。
   - 「自定义 API 中转站」：单独一个入口，只列支持自定义网关的 CLI，这里才出现 Base URL、Key、模型等字段。
4. **Codex 识别不到，是因为本机的 codex 不在 PATH 上**，它装在 `/Applications/ChatGPT.app/Contents/Resources/codex` 里。参考实现 守护进程对 codex 专门兜底扫了 ChatGPT.app / Codex.app 的包内路径，Multara 的 `runtime.rs` 只查了 PATH 和登录 shell 的 PATH，所以漏了。

## 2. 现状对比

### 2.1 参考实现 的添加流程

代码：`参考仓库/packages/views/runtimes/components/runtime-profiles-dialog.tsx`、`runtime-profile-catalog.ts`

- 第 1 步：选基础运行时，网格列出 `RUNTIME_PROFILE_RUNTIME_TYPES`（`packages/core/types/agent.ts`），共 36 个：
  `claude, codebuddy, codex, copilot, opencode, codearts, deveco, openclaw, hermes, pi, cursor, kimi, reasonix, dsh, dim, kiro, antigravity, qoder, qoderclicn, traecli, grok, qwen, qwenpaw, mcode, zeroclaw, omp`
- 第 2 步：表单只有三项：
  - **显示名称**（必填，工作区内唯一，重名返回 409）
  - **命令行**（必填，单行输入，比如 `agent --model composer-2.5`；前端用 `parseCommandLine` 拆成 `command_name` + `fixed_args`，下方实时预览"可执行文件 / 固定参数"，禁止 `$`、反引号、`| > < ; &`）
  - **描述**（可选）
- 基础运行时创建后锁定，不能改。
- 运行时 `fixed_args` 拼在 argv **最前面**，后面才是内置的启动参数（`server/pkg/agent/launch_test.go` 里有约束："fixed_args must be the argv prefix"）。所以自定义 profile 不会丢掉 `--output-format stream-json` 这类协议参数。
- 弹窗还有一个「管理」视图：左边列表（先列自定义，内置的折叠成"参考"），右边是详情、编辑和删除。

### 2.2 Multara 的添加流程

代码：`src/views/CreateRuntimeDialog.vue`、`src/views/runtime-catalog.ts`、`src-tauri/src/executor.rs`

- 第 1 步：9 个选项 `claude, codex, cursor, copilot, opencode, gemini, qwen, kimi, custom`。
- 第 2 步：所有选项共用同一张大表单：名称、命令、API 协议、Base URL、Key、模型、固定参数（多行）、环境变量、最大并发。
- 存储：`custom_runtimes` 表（`provider, protocol, api_url, api_key, models_json, env_json, args_json`）。
- 执行（`executor.rs::execution_for`）：
  - 固定参数为空：用 `build_args(provider)`，也就是内置参数。
  - 固定参数非空：**直接替换掉内置参数**，再把 prompt 追加到末尾。这会让基于 Cursor/Claude 的自定义运行时丢掉 `-p --output-format stream-json`，输出解析就失效了。和 参考实现 的"前缀"语义不一致，需要修。

### 2.3 Multara 后端实际能驱动的 CLI

`executor.rs::normalize_runtime_line` 只认识 `claude / cursor / codex / qwen / gemini` 这 5 种输出格式。`copilot / opencode / kimi` 只走 `_ => vec![assignment]`，没有专门的启动参数，也没有输出解析。**所以 UI 上把 参考实现 的 36 个全部列出来，不代表都能跑**，需要分期做（见第 6 节）。

## 3. 目标交互

### 3.1 第 1 步：选择方式

弹窗顶部分两组：

```
基于内置运行时（和 参考实现 一致）
[Claude] [Codex] [Cursor] [Copilot] [OpenCode] [Gemini] [Qwen] [Kimi] ...（参考实现 全量）
  └ 后端还没适配的显示「即将支持」，置灰不可点

自定义 API 中转站
[🔌 自定义 API 中转站]   ← 单独一张卡片，说明：使用第三方/公司网关的 Base URL + Key
```

现在的 `custom`（"自定义命令"）选项去掉，原因有两个：
- 任意命令 Multara 都解析不了它的输出，跑起来也看不到时间线；
- 想"换个命令名或包装脚本"，可以选一个内置运行时，命令行填自己的脚本，和 参考实现 的做法一样。

### 3.2 第 2 步 A：基于内置运行时（参考实现 同款）

| 字段 | 说明 |
| --- | --- |
| 基础运行时 | 只读，显示图标和名称，提示"创建后不可更改" |
| 显示名称 | 必填，默认填运行时名称，重名报错 |
| 命令行 | 必填，单行，例如 `claude --model opus` 或 `/usr/local/bin/my-claude`；下方预览可执行文件和固定参数；命令找不到时给出提示（不阻止保存） |
| 描述 | 可选 |
| 最大并发 | 保留（Multara 特有），放进「高级」折叠区，默认 2 |

不显示 API 协议、Base URL、Key、模型、环境变量。

### 3.3 第 2 步 B：自定义 API 中转站

先选"用哪个 CLI 来连这个中转站"，**只列支持自定义网关的 CLI**，协议由 CLI 自动决定，不再让用户选：

| CLI | 协议 | 注入方式（需逐个实测） |
| --- | --- | --- |
| Claude Code | Anthropic | `ANTHROPIC_BASE_URL`，`ANTHROPIC_AUTH_TOKEN`（大多数中转站用 Bearer；保留"用 x-api-key"开关时改写 `ANTHROPIC_API_KEY`），`ANTHROPIC_MODEL` |
| Codex | OpenAI Responses / Chat | 用 `-c` 覆盖配置：`model_provider=multara`、`model_providers.multara.base_url=…`、`model_providers.multara.env_key=MULTARA_GATEWAY_KEY`、`model_providers.multara.wire_api=responses\|chat`，模型用 `-m`。**Codex 不读 `OPENAI_MODEL`**，现在的写法里模型那一项不生效 |
| Gemini CLI | Gemini | `GOOGLE_GEMINI_BASE_URL`、`GEMINI_API_KEY`、`GEMINI_MODEL` |
| Qwen Code | OpenAI 兼容 | `OPENAI_BASE_URL`、`OPENAI_API_KEY`、`OPENAI_MODEL` |

Cursor、Copilot 不支持接自己的网关，不出现在这一组。OpenCode 走配置文件（`OPENCODE_CONFIG_CONTENT`），放到第二期。

表单字段：

| 字段 | 说明 |
| --- | --- |
| CLI | 上表里的一个，切换后显示该 CLI 对应的示例 URL |
| 显示名称 | 必填 |
| API Base URL | 必填，保存时去掉末尾的 `/`；按 CLI 提示是否要带 `/v1` |
| API Key | 必填，密码框，编辑时显示"已保存，留空表示不修改" |
| 模型 | 可选，每行一个，第一个是默认模型；也作为模型选择器的选项来源（沿用 `custom_runtime_models`） |
| Codex 专属：接口类型 | `responses` / `chat`，默认 `responses` |
| 高级（折叠） | 命令行（默认就是 CLI 命令）、额外环境变量 `KEY=VALUE`、最大并发 |
| 测试连接（可选） | 按钮，用当前配置跑一次最小 prompt，显示成功或错误信息 |

### 3.4 列表 / 管理视图

参考 参考实现：运行时列表里自定义项显示「名称 + 基础 CLI 小字」，中转站类型多加一个「中转站」标签和 Base URL 的主机名。编辑时不能修改「方式」和「基础 CLI」。

## 4. 数据与后端改动

### 4.1 表结构（`database.rs`）

`custom_runtimes` 加两列：

```sql
kind        TEXT NOT NULL DEFAULT 'profile'   -- 'profile' | 'gateway'
description TEXT NOT NULL DEFAULT ''
```

旧数据迁移规则（用 `ensure_column` 之后跑一次 UPDATE）：
- `api_url != '' OR api_key != ''` → `kind = 'gateway'`
- 其余 → `kind = 'profile'`
- `provider = 'custom'` 的旧行保持能运行，但 UI 显示"旧版自定义命令"，只能删除或改为基于某个内置运行时。

`protocol` 列保留，但不再由用户选择，保存时按 `provider` 推导（`claude→anthropic`、`codex→openai`、`gemini→gemini`、`qwen→openai`）。

### 4.2 `CustomRuntimeInput` / `CustomRuntimeForm`（`models.rs`、`commands.rs`）

- 新增 `kind`、`description`。
- `kind = 'profile'` 时后端**忽略并清空** `api_url / api_key / models / env`，避免旧值残留并在运行时被注入。
- `kind = 'gateway'` 时校验 `provider` 在支持网关的白名单里，`api_url` 非空。
- 名称重复时返回明确的错误（目前没有这条校验）。

### 4.3 启动参数（`executor.rs::execution_for`）

改成和 参考实现 一样的"固定参数前缀"语义：

```rust
let mut args = launch.args.clone();               // 用户的固定参数在最前
args.extend(runtime::build_args(&launch.provider, assignment)); // 内置参数和 prompt 在后
if launch.kind == "gateway" {
    args.extend(runtime::gateway_args(&launch));  // 例如 Codex 的 -c / -m
}
```

`prompt_via_stdin` 继续按 `provider` 判断。环境变量注入改为调用新的 `runtime::gateway_env(provider, …)`，替代现在按 `protocol` 分支的 `protocol_env`，同时修正 Claude 用 `AUTH_TOKEN`、Codex 不用 env 指定模型这两个问题。

### 4.4 前端

- `runtime-catalog.ts`：
  - `RUNTIME_FAMILIES` 改为 参考实现 的全量列表，每项带 `supported: boolean`、`gateway: boolean`、`command`、`protocol`。
  - 移植 参考实现 的 `parseCommandLine` / `formatCommandLine` 和它的单测（`runtime-profile-catalog.test.ts` 可以直接参考）。
  - 删掉 `RUNTIME_PROTOCOLS` 选择和 `protocolEnv`，网关环境变量全部由后端生成。
- `CreateRuntimeDialog.vue`：状态改为 `step: "kind" | "profile" | "gateway"`，两张表单拆成两个子组件，避免继续写 `v-if` 堆叠。
- `ProviderLogo.vue`：补齐新增运行时的图标（参考实现 在 `packages/views/runtimes/components/provider-logo.tsx` 和同目录的 png/svg 资源里）。
- i18n：新增 `runtime.kind.*`、`runtime.gateway.*`、`runtime.field.description`、`runtime.field.commandLine` 以及命令行解析错误文案；删除 `runtime.protocol.*` 选择相关文案。

## 5. Codex 识别修复

### 5.1 参考实现 的做法

`参考仓库/server/internal/daemon/agents_probe.go` 的 `probe` 依次尝试：

1. `CODEX_PATH_OVERRIDE` 环境变量覆盖；
2. 当前进程 PATH（`exec.LookPath`）；
3. 登录 shell 解析出来的 PATH（处理 nvm / fnm / `~/.local/bin`，带 TTL 缓存）；
4. **codex 专用兜底**：`codexDesktopAppBundlePaths()`（`config.go`），按顺序检查：
   ```
   /Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
   /Applications/ChatGPT.app/Contents/Resources/codex
   /Applications/Codex.app/Contents/Resources/codex
   ~/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex
   ~/Applications/ChatGPT.app/Contents/Resources/codex
   ~/Applications/Codex.app/Contents/Resources/codex
   ```
   第一个存在且可执行的就用。

本机实测：`which codex` 找不到，`/Applications/ChatGPT.app/Contents/Resources/codex` 存在，所以 参考实现 能识别，Multara 不能。

### 5.2 Multara 的改法（`src-tauri/src/runtime.rs`）

- `RuntimeSpec` 加一个 `fallback_paths: fn() -> Vec<PathBuf>`，codex 填上面 6 个路径（macOS 下），其他运行时返回空。
- `detect_spec` 和 `execution` 在 `resolve_command` 失败后再遍历 `fallback_paths`，检查"是文件 + 有可执行位"。
- 自定义运行时：命令是裸名 `codex`、`provider = codex` 时也走同一个兜底，否则基于 Codex 的 profile 和中转站同样会显示"未找到"。
- 预留覆盖：支持环境变量 `MULTARA_CODEX_PATH`（和 参考实现 的 `*_PATH 覆盖` 一致），设置了就只用它，不存在就直接判定未找到，不回退。
- 现在的 `command_path_cache` 会把"未找到"也缓存住，用户后来装了 CLI 也得重启才能识别。改成只缓存命中的结果，或者加 TTL（参考实现 用的是 TTL）。
- 加单测：用临时目录伪造 bundle 路径，验证 PATH 找不到时兜底能命中，以及设置了覆盖变量时不回退。

## 6. 分期

| 阶段 | 内容 |
| --- | --- |
| 第一期 | Codex 包内路径识别；弹窗拆成「内置运行时 / 自定义中转站」两种方式；命令行单行解析；固定参数改为前缀语义；`kind` / `description` 字段和旧数据迁移；中转站支持 Claude / Codex / Gemini / Qwen |
| 第二期 | 目录补齐 参考实现 全量列表（未适配的置灰显示"即将支持"）；OpenCode 中转站；测试连接按钮；管理视图（列表 + 详情） |
| 第三期 | 逐个适配新 CLI 的启动参数和输出解析（`build_args` + `normalize_*`），适配一个就放开一个，优先 Copilot、OpenCode、Kimi |

## 7. 验证清单

- 本机不在 PATH 的 codex 显示为「在线」，路径指向 ChatGPT.app。
- 基于 Cursor 建一个 profile，命令行填 `cursor-agent --model composer-2.5`，任务能跑，时间线正常（验证固定参数前缀语义）。
- Claude 中转站：填 Base URL + Key，任务请求打到网关；Key 不出现在日志里（沿用 `truncate_and_redact`）。
- Codex 中转站：`responses` 和 `chat` 两种接口类型各跑一次，模型生效。
- 旧数据：已有带 `api_url` 的自定义运行时升级后显示为中转站，且仍能运行。
- 新表单类型下切换 CLI，不会把上一个 CLI 的网关字段带过去。
