# 聊天里多文件「正在编辑」状态展示现状

智能体同时改多个文件时，参考产品会同时列出好几行「Editing xxx」，每行一直扫光到这一批改完。Multara 实际使用中几乎看不到这种画面，通常是改完一个文件出现一张卡片，再改下一个。

本文记录现状和原因，不改代码。

---

## 1. 界面已经能显示多个

前端不限制同时进行的修改数量。

- **时间线**：`timeline-display.ts` 的 `buildEventTree` 按 `callId` 把 `tool_use` 和 `tool_result` 配成一个节点，和先后顺序无关。每次修改各自一张 `FileDiffCard`，没有结果时显示「编辑文件 xxx」，有结果后显示「修改 xxx」和 diff。
- **底部运行状态**：`pendingEditNames` 收集所有还没有结果的修改，`liveWorkParts` 给每个文件生成一行，`ChatPanel.vue` 逐行扫光显示。任务详情 `TaskActivity` 用的是同一个函数。
- 连续的读取、搜索合并成一个「已探索」分组（`ExploreGroup`）。

所以问题不在界面，而在于界面收到「正在编辑」这个状态的时间太晚、持续得太短。

---

## 2. 实测数据

数据来自本机 `multara.sqlite3` 的 `run_events`（只读查询，2026-11-13）。

| 运行时 | 编辑次数 | 编辑出现前的间隔（模型在生成修改内容） | 编辑出现到结果返回（界面显示「编辑文件」） | 与另一处修改同时进行 |
| --- | --- | --- | --- | --- |
| Claude（AI 网关自定义运行时） | 253 | 平均 8.0 秒 | 平均 1.2 秒（`Write` 0.2 秒） | 45 次，约 18% |
| Cursor | 220 | 平均 3.1 秒 | 平均 2.1 秒 | 11 次，5% |
| Codex | 5 次运行 | — | — | 没有任何编辑事件 |

「编辑出现前的间隔」是这条 `tool_use` 和它前一条事件的时间差，大部分是模型在写这次修改的参数（`old_string` / `new_string` 等）。

---

## 3. 原因

### 3.1 最耗时的阶段界面不知道在编辑

Claude 以 `--output-format stream-json` 运行（`runtime.rs` 约 681 行），没有加 `--include-partial-messages`。CLI 只在一个内容块完整生成后才输出这条 `tool_use`。

一次修改的时间分布：

1. 模型生成修改参数：平均 8 秒。界面不知道这是一次编辑，底部状态停留在上一个动作上。
2. Multara 收到 `tool_use`：「编辑文件 xxx」出现。
3. CLI 执行修改：很快，1 秒左右。
4. 收到 `tool_result`：卡片变成「修改 xxx」。

用户看到的就是：等一段时间，「编辑文件」闪一下，变成已完成的卡片，再开始下一个文件。

参考产品在模型**开始**生成某个调用时就显示一行，同一轮里连着发出的几个编辑会一起保持进行中，直到这一批执行完。这需要流式拿到调用开始事件。

### 3.2 模型本来多数是串行修改

就算只看「已出现、未返回」这段时间，Claude 只有约 18% 的修改和另一处修改重叠，Cursor 只有 5%。每次重叠也只有一两秒，肉眼几乎看不到多行同时出现。

### 3.3 Codex 的修改完全不进时间线

Codex 以 `exec --json` 运行，改文件报的是 `file_change` 类型的 item，`changes` 数组里可以一次带多个文件。`executor.rs` 的 `normalize_codex` 只处理 `agent_message`、`reasoning`、`command_execution`、`mcp_tool_call`、`tool_call`，`file_change` 落到 `_ => Vec::new()` 被丢弃。全仓库没有 `file_change` 的处理。

结果：用 Codex 时，聊天里没有修改卡片，也没有「编辑文件」状态。另外 Codex 一般在改完时才发 `file_change`，补上之后也只能显示「修改 a、b、c」，做不出进行中的状态。

### 3.4 前端的两个小问题

- `pendingEditNames` 按文件名（basename）去重，不是按完整路径。两个目录下的 `index.ts` 同时在改，底部状态只显示一行。
- 底部状态只在 `liveStageKey` 判定为「编辑」阶段时才逐文件列出。修改还没返回、最新事件已经是一次读取时，状态显示「读取 …」，未完成的修改不再列出。

---

## 4. 已有但不可用的增量处理

`executor.rs` 的 Claude 解析已经处理 `content_block_start`（`tool_use`）和 `content_block_delta`（`input_json_delta`），前端 `coalesceTimeline` 会把没有 `callId`、没有工具名的 `tool_use` 片段拼到前一条上。但目前：

- 启动参数没有 `--include-partial-messages`，这些事件实际不会出现。
- `input_json_delta` 取 `callId` 用的是 `/content_block/id`，增量事件里没有这个字段，只有 `index`。现在靠前端「拼到前一条」兜底，内容块交错时会拼错。
- 每个增量都会成为一条事件。如果直接打开，`run_events` 的行数会大幅增加。
- 增量阶段参数是不完整的 JSON，`toolPath` 解析不出路径，卡片只能显示「编辑文件」，没有文件名。

---

## 5. 要做出参考产品的效果需要什么

| 事项 | 涉及位置 | 说明 |
| --- | --- | --- |
| Claude 打开增量输出 | `runtime.rs` 启动参数 | 加 `--include-partial-messages`，模型一开始写调用就能收到 `content_block_start` |
| 增量按 `index` 对回调用 | `executor.rs` Claude 解析 | 记住 `index → call_id / tool`，增量带上正确的 `callId` |
| 增量只在内存里拼接 | 事件落库 | 生成过程中推给前端，内容块结束后只落一条完整的 `tool_use` |
| 从半截 JSON 提取路径 | `timeline-display.ts` | `file_path` / `path` 一出现就显示文件名 |
| Codex 处理 `file_change` | `executor.rs` `normalize_codex` | `changes` 里每个文件拆成一条修改记录，进时间线和改动追踪 |
| 进行中的修改按完整路径去重 | `pendingEditNames` | 同名不同目录分别显示 |
| 有未完成的修改时优先列出 | `liveWorkParts` | 不因最新事件变成读取而隐藏 |

Cursor 的流式输出里有没有「开始生成调用参数」的事件，还没有确认。从第 2 节的数据看（编辑出现前平均有 3 秒间隔），它的 `tool_call started` 很可能也是在参数生成完以后才发，效果和 Claude 现状一样。
