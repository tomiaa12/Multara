# 工作流（节点编排）技术方案与实施文档

> 状态：已实现（PR #2）· 文中凡与代码不一致之处以代码为准，第 16 节列出实现时相对初稿的调整。
> 范围：在 Multara 内新增「工作流」能力——在画布上用节点和连线编排智能体、脚本、人工审批、分支、循环、子流程，一次性完整交付。

---

## 0. 目标与边界

### 0.1 要解决的问题

现有协作方式全部由 LLM 现场决定下一步：

| 机制 | 实现 | 问题 |
|---|---|---|
| 小队 `@成员` 派活 | `executor.rs` `dispatch_mentions`（约 2970 行）解析回答里以 `@` 开头的段落；`resume_leader_after_members`（约 2861 行）成员收口后唤醒队长 | 流程不确定；派活最多 3 层；成员间只靠聊天文本传递 |
| 父子任务汇总 | `ops/task.rs` `maybe_resume_parent`（353 行） | 只能「全部子任务收口后汇总一次」，无顺序、无分支 |
| 自动化 | `commands.rs` `start_automation_run`（约 6597 行） | 只触发一个智能体/小队的一段 prompt |

缺的是：**固定可复现的流程、节点间结构化数据契约、确定性判定（退出码而不是 agent 自述）、循环上限、人工关卡、从失败节点重试、全程可观察**。

### 0.2 目标

1. 通用节点模型：引擎只认识十几种**节点类型**；「读需求 / 看 Figma / 写代码 / 测试 / 部署」都是**节点模板**（预配置的节点），不写死在引擎里。
2. 每个节点**多输入、多输出**，端口有类型，可带 JSON Schema。
3. 支持顺序、并行、条件分支、汇合、有上限的循环、人工审批、子流程、对列表并行（Map）。
4. 最大化复用现有能力：智能体运行队列、会话/聊天 UI、工作区与 worktree、Plan 审批、收件箱、自动化触发、飞书渠道、`multara` CLI、用量统计。
5. 全部状态落 SQLite，应用重启后可继续；任意节点可重试；每次运行可回放。

### 0.3 非目标

- 不做通用 iPaaS（不内置几百个 SaaS 连接器，外部系统用 HTTP / Script / MCP 智能体接）。
- 不引入新的模型调用通道：一个「LLM 步骤」就是一个 Agent 节点，仍然是 spawn 本机 CLI。
- 不做多用户协同编辑（Multara 是本地单用户应用）。

### 0.4 选型结论

| 候选 | 结论 |
|---|---|
| Tencent LoopForge | 概念最接近（SOP = 角色 agent + 脚本 + 子 SOP + 人工关卡；脚本退出码判定）。它是 Docker 自托管平台，与 Multara 本地桌面 + 本机 worktree 的模型不同。**借鉴设计，不嵌入。** |
| Langflow / Dify / Flowise / n8n | 节点是秒级无状态 LLM/API 调用，没有工作区、git、长时 CLI 会话、审批会话的概念。**不适用。** |
| 自研（本方案） | Rust 引擎 + SQLite + Vue Flow 画布，直接挂在现有执行器上。 |

## 1. 核心概念

| 术语 | 含义 |
|---|---|
| **工作流（Workflow）** | 一张有向图定义：节点、连线、工作流输入/输出、工作区槽位、设置。有草稿和不可变的已发布版本。 |
| **版本（Version）** | 发布时冻结的定义快照。运行永远绑定一个版本，编辑草稿不影响正在跑的运行。 |
| **运行（Run）** | 某版本的一次执行。 |
| **节点（Node）** | 图中的一个步骤，有类型（kind）、配置、输入端口、输出端口。 |
| **节点运行（NodeRun）** | 节点在某次运行里的一次执行，以 `(node_id, iteration, attempt)` 区分（循环产生新 iteration，重试产生新 attempt）。 |
| **端口（Port）** | 节点的命名输入/输出，带类型。另有隐式控制端口 `$in` / `$out`。 |
| **连线（Edge）** | 从某节点输出端口到另一节点输入端口。指向祖先节点的连线是**回边**，只能从 Switch / Gate 发出，用于循环。 |
| **值（Value）** | 端口上产生的数据，存 `workflow_values`；大值落文件。 |
| **工作区槽位（Workspace Slot）** | 工作流级别声明的代码目录（来自某个需求的 Git 仓库/文件夹），运行开始时准备成 worktree，节点声明对它读或写。 |
| **节点模板（Node Template）** | 预填好的节点（类型 + prompt + 端口 + 推荐智能体资源），在节点库里拖出来用。 |

> 与上一版口头方案的差异：上一版把 `workspace` 设计成一种端口类型。细化后改成**工作区槽位**——工作区是被多个节点共享修改的状态，不是一次性传递的数据；做成槽位后，引擎能统一做加锁、自动提交、按节点回滚。节点仍然可以通过模板变量 `{{ ws.app.head }}` 等读到分支/提交信息。

## 2. 工作流定义（DSL）

定义以 JSON 存储（`workflows.draft_json`、`workflow_versions.definition_json`），也可导入导出为 `.multara-flow.json` 文件。下面是完整结构。

### 2.1 TypeScript 类型（`src/domain/workflow.ts`）

```ts
export type PortType =
  | "text" | "markdown" | "number" | "boolean"
  | "json" | "url" | "file" | "files" | "any";

export interface PortDef {
  name: string;               // 节点内唯一，[a-zA-Z_][a-zA-Z0-9_]*
  type: PortType;
  label?: string;
  description?: string;       // 会写进 agent 的节点简报
  required?: boolean;         // 输入端口：未连线且无默认值时校验失败；输出端口：agent 必须提交
  schema?: JsonSchema;        // type=json 时可选，运行时校验
  multi?: boolean;            // 仅输入端口：允许多条连线，值聚合为数组
  default?: unknown;          // 仅输入端口
}

export type NodeKind =
  | "trigger" | "output"
  | "agent" | "script" | "gate" | "switch"
  | "transform" | "http" | "git" | "notify"
  | "subflow" | "map" | "note";

export interface WorkspaceUse { slot: string; access: "read" | "write"; fork?: boolean }

export interface RetryPolicy { maxAttempts: number; backoffSeconds: number; on: ("failed" | "timeout")[] }

export interface NodeDef {
  id: string;                 // 定义内唯一，[a-z][a-z0-9_]*，模板变量里用
  kind: NodeKind;
  title: string;
  description?: string;
  inputs: PortDef[];
  outputs: PortDef[];
  config: NodeConfig;         // 按 kind 不同，见第 4 节
  workspaces?: WorkspaceUse[];
  join?: "all" | "any";       // 默认 all
  timeoutMinutes?: number;    // 默认见各类型
  retry?: RetryPolicy;        // 默认 {maxAttempts:1}
  onError?: "fail_run" | "continue"; // continue：失败时走 $error 端口，不让整个运行失败
  templateId?: string;        // 来源模板（仅展示用）
  position: { x: number; y: number };
}

export interface EdgeDef {
  id: string;
  source: string; sourcePort: string;   // 可为 "$out" / "$error" / 分支端口
  target: string; targetPort: string;   // 可为 "$in"
  maxIterations?: number;                // 仅回边，必填，1~20
}

export interface WorkspaceSlotDef {
  key: string;                // 槽位名，如 "app"
  label: string;
  project: string;            // 需求 id，或模板 "{{ run.inputs.project }}"
  workspace?: string;         // 需求下工作区名称（多仓需求时选哪一个），空 = 第一个
  isolation: "worktree_new" | "worktree_existing" | "direct";
  baseRef?: string;           // worktree_new 的起点，默认当前分支
  branch?: string;            // 模板，默认 "wf/{{ workflow.slug }}-{{ run.short_id }}"
  autoCommit?: boolean;       // 写节点成功后自动提交，默认 true
}

export interface WorkflowDef {
  schemaVersion: 1;
  inputs: PortDef[];          // 运行入参（手动运行时渲染成表单）
  outputs: PortDef[];         // 运行出参（由 output 节点填）
  workspaces: WorkspaceSlotDef[];
  nodes: NodeDef[];
  edges: EdgeDef[];
  settings: {
    ownerAgentId: string;     // 总览会话、任务卡片的负责人；默认 Miku
    maxParallelNodes: number; // 默认 4
    runTimeoutMinutes?: number;
    concurrency: "allow" | "skip_if_running" | "queue"; // 同一工作流多次触发的策略，默认 queue
  };
}
```

Rust 侧在 `src-tauri/src/workflow/model.rs` 定义对应的 `serde` 结构（`#[serde(rename_all = "camelCase", deny_unknown_fields)]`），`config` 用带 `kind` 标签的枚举：

```rust
#[derive(Serialize, Deserialize, Clone)]
#[serde(tag = "kind", content = "config", rename_all = "snake_case")]
pub enum NodeConfig {
    Trigger(TriggerConfig), Output(OutputConfig), Agent(AgentConfig),
    Script(ScriptConfig), Gate(GateConfig), Switch(SwitchConfig),
    Transform(TransformConfig), Http(HttpConfig), Git(GitConfig),
    Notify(NotifyConfig), Subflow(SubflowConfig), Map(MapConfig), Note(NoteConfig),
}
```

（`NodeDef` 在 Rust 里把 `kind` + `config` 合并成 `NodeConfig`，序列化格式与 TS 一致。）

### 2.2 端口类型与兼容性

| 来源 \ 目标 | text | markdown | number | boolean | json | url | file | files | any |
|---|---|---|---|---|---|---|---|---|---|
| text | ✓ | ✓ | | | | | | | ✓ |
| markdown | ✓ | ✓ | | | | | | | ✓ |
| number | ✓ | ✓ | ✓ | | ✓ | | | | ✓ |
| boolean | ✓ | ✓ | | ✓ | ✓ | | | | ✓ |
| json | ✓¹ | ✓¹ | | | ✓² | | | | ✓ |
| url | ✓ | ✓ | | | | ✓ | | | ✓ |
| file | ✓³ | ✓³ | | | | | ✓ | ✓⁴ | ✓ |
| files | | | | | ✓ | | | ✓ | ✓ |
| any | ✓⁵ | ✓⁵ | ✓⁵ | ✓⁵ | ✓⁵ | ✓⁵ | ✓⁵ | ✓⁵ | ✓ |

1. 序列化为格式化 JSON 文本。2. 两端都有 schema 时只做「目标 required 字段在来源 schema 中存在」的静态检查，运行时按目标 schema 严格校验。3. 传文件路径文本。4. 包成单元素数组。5. 运行时检查，不符合则节点失败（`type_mismatch`）。

`multi: true` 的输入端口值为 `Array<来源值>`，顺序按连线在定义中的顺序。

### 2.3 模板语言

所有字符串配置（prompt、命令、URL、分支名、条件表达式）都用 **MiniJinja**（Rust crate `minijinja`，Jinja2 语法），开启 `UndefinedBehavior::Strict`。上下文：

| 变量 | 内容 |
|---|---|
| `inputs.<port>` | 当前节点输入端口的值（`multi` 端口为数组） |
| `nodes.<id>.outputs.<port>` | 任一**上游**节点的输出（静态校验保证只能引用祖先） |
| `nodes.<id>.status` | 上游节点状态 |
| `run.inputs.<name>` / `run.id` / `run.short_id` / `run.started_at` | 运行信息 |
| `workflow.name` / `workflow.slug` / `workflow.version` | 工作流信息 |
| `ws.<slot>.path` / `.branch` / `.head` / `.base` | 工作区槽位当前状态 |
| `iteration` / `attempt` | 当前节点运行的循环轮次（从 0 开始）、重试次数（从 1 开始） |
| `item` / `index` | 仅 Map 的子流程里：当前元素、下标 |

函数和过滤器：`secret("NAME")`（只允许在 script 的 env、http 的 headers/url/body 里用，其他地方使用会在校验时报错）、`tojson`、`fromjson`、`shell_quote`、`truncate(n)`、`default(v)`、`jsonpath("$.a[0]")`。

Switch 条件、Transform 表达式使用 `Environment::compile_expression`，与模板同一套语法和上下文。

前端不重复实现模板引擎：编辑器的「预览渲染」和自动补全通过 `workflow_render_preview` 命令交给后端（第 9 节）。

## 3. 执行语义

### 3.1 节点运行状态

```
pending ──就绪判定──▶ ready ──取得并发/工作区锁──▶ running ──▶ succeeded
   │                                           │          ├──▶ failed ──(retry)──▶ 新 attempt pending
   │                                           │          └──▶ waiting_human ──决定──▶ succeeded / failed
   │                                           └──▶ waiting_children（subflow / map）──▶ succeeded / failed
   └──所有入边死亡──▶ skipped
任意非终态 ──取消──▶ cancelled
上游重试/循环复用 ──▶ reused（只用于展示，值引用原节点运行）
```

运行状态：`queued → running ⇄ waiting（有 waiting_human 节点且无 running 节点）→ succeeded | failed | cancelled`。

### 3.2 「当前节点运行」

每个节点在一次运行中可能有多条 node_run（循环 iteration、重试 attempt）。**当前节点运行** = `iteration` 最大、其次 `attempt` 最大的那一条。所有判定、取值都只看当前节点运行。

### 3.3 连线存活判定

对目标节点 N 的每条**非回边**入边 e（来源 S）：

| S 当前节点运行状态 | e 的状态 |
|---|---|
| 不存在 / pending / ready / running / waiting_* | **未决** |
| skipped / cancelled | **死** |
| failed 且 S.onError=continue | `sourcePort == "$error"` 为**活**，其余为**死** |
| failed 且 S.onError=fail_run | 运行已失败，不再判定 |
| succeeded / reused | 分支类节点（switch、gate）：`sourcePort` 在 `fired_ports` 里或是非分支数据端口为**活**，否则**死**；其他节点：`$error` 死，其余全**活** |

### 3.4 就绪判定（`join`）

- 没有非回边入边的节点（trigger、或孤立入口）：运行开始时直接 ready。
- `join = "all"`（默认）：存在未决入边 → 等待；全部入边死 → **skipped**；否则检查每个 `required` 输入端口至少有一条活入边或有默认值，满足 → **ready**，不满足 → **skipped**（记录 `reason=required_input_dead`）。
- `join = "any"`：任一入边为活 → ready（其余未决入边到达时忽略，不会再次触发）；全部死 → skipped。

skipped 会继续向下游传播（下游再判定时看到死边）。

### 3.5 输入取值

N 就绪后，对每个输入端口按顺序取值：
1. 活入边来源的当前节点运行在该 `sourcePort` 上的值（`multi` 端口聚合全部活入边）；
2. 回边带来的值（见 3.6，仅 iteration>0）；
3. 端口 `default`；
4. 都没有：`required` → 节点失败 `missing_input`；否则为 `null`。

取到的输入快照写进 `workflow_node_runs.inputs_json`，之后重放、调试都看快照，不再重新求值。

### 3.6 循环（回边）

回边 `X.port → T.targetPort`，X 必须是 switch 或 gate，T 必须是 X 的祖先（含 X 自身之外的任意祖先），`maxIterations` 必填。

当 X 的当前节点运行触发了 `port`：
1. 读 `workflow_loop_counters(run_id, edge_id)`，若 `count >= maxIterations`：本次不走回边，改为触发 X 的 `exhausted` 端口（switch/gate 都隐式带这个端口；没有连线则运行失败，`error_code=loop_exhausted`）。
2. 否则 `count += 1`，计算 **D = T 在前向图（去掉所有回边）中的全部后代 ∪ {T}**；对 D 中每个节点新建 node_run：`iteration = 当前 iteration + 1, attempt = 1, status = pending`。D 中仍处于 running / waiting 的旧节点运行先取消（正常情况下不会有，因为 X 在它们下游）。
3. 回边携带的值 = X 该端口的值（switch 的分支端口值 = switch 的 `value` 输入；gate 的分支端口值 = `{decision, comment, form}`），写入 T 新节点运行的对应输入端口。
4. 工作区：D 中写节点的工作区不回滚——循环的本意就是「在当前代码基础上继续改」。

典型用法：`test → check(switch)`，`check.fail ──回边(max 3)──▶ code.feedback`；`review(gate).changes ──回边(max 5)──▶ code.feedback`。

### 3.7 重试

- 自动重试：节点失败且 `retry.maxAttempts > attempt`、失败原因在 `retry.on` 里 → `backoffSeconds * 2^(attempt-1)` 秒后新建 `attempt+1` 的 node_run（同 iteration）。
- 手动重试（运行视图「从这里重试」）：对目标节点 N 新建 attempt+1，同时对 N 的全部前向后代新建 attempt+1（pending）；N 声明写访问的槽位 `git reset --hard <N 当前节点运行的 workspace_before>`（需用户在确认框里勾选「丢弃该节点之后的代码改动」）。运行状态从 failed/cancelled 回到 running。
- 重试后的新节点运行，其上游值仍取上游当前节点运行，上游不重跑。

### 3.8 取消与超时

- 取消运行：所有非终态节点运行标为 cancelled；agent 节点调用现有停止运行的逻辑（与聊天里「停止」按钮同一条路径）；script 进程树 kill（复用 `executor.rs` 的 `kill_process`）；gate 关闭对应的收件箱待办。
- 节点超时：`deadline_at` 到期由引擎定时器（3.10）处理，等同取消该节点 + 失败 `error_code=timeout`，再走重试策略。默认超时：agent 120 分钟、script 30 分钟、http 2 分钟、gate 不超时（可配 `timeoutMinutes` + `onTimeout: approve|reject|fail`）。
- 运行超时：`settings.runTimeoutMinutes`，到期取消整个运行。

### 3.9 并发与工作区锁

- 每次运行最多 `settings.maxParallelNodes` 个节点同时 running；agent 节点还会受现有运行时/智能体并发上限约束（执行器队列本身就做了，见 `dispatch_pending`）。
- 工作区锁：同一槽位同一时刻只能有**一个写节点**在 running；读节点不加锁（读到的是当前磁盘状态）。拿不到锁的节点停在 ready。
- 需要并行改代码时，节点设 `fork: true`：引擎在该槽位当前 head 上建一个临时 worktree（分支 `<槽位分支>-<node_id>-<iteration>`），节点写在那里，不占主锁；完成后输出端口 `branch`（text），由下游 `git` 节点 `merge` 回主槽位。
- 静态校验会检查：两个都写同一槽位、彼此之间又没有路径（可能并行）的非 fork 节点 → 警告「运行时会被串行化」。

### 3.10 引擎驱动方式

引擎是**事件驱动 + 定时兜底**，核心函数 `engine::advance(app, run_id)` 幂等：

```
advance(run):
  lock run_mutex(run_id)                       # 同一运行串行推进
  tx = db.transaction()
  loop:
    progressed = false
    for node in topo_order(def without back edges):
      nr = current(node)
      if nr.status == pending:
        match readiness(node):
          Wait   -> continue
          Skip   -> nr.status = skipped; progressed = true
          Ready  -> nr.inputs = resolve_inputs(node); nr.status = ready; progressed = true
    for nr in ready nodes ordered by topo index:
      if running_count >= maxParallel: break
      if needs write lock and lock held: continue
      start(nr)    # 各节点类型的启动：入队 agent_run / spawn 脚本线程 / 创建审批 / 立即计算
      progressed = true
    if not progressed: break
  update run status (all terminal → succeeded/failed; any waiting_human & none running → waiting)
  tx.commit()
  emit events
```

调用 `advance` 的时机：
1. 运行创建后；
2. agent 节点所属会话的 agent_run 结束（挂在 `executor::finish` 里，见 7.2）；
3. script / http / git 节点后台线程结束；
4. gate 被决定；
5. 子运行结束（subflow / map）；
6. `workflow::engine::tick`：复用 `automation.rs` 的 30 秒循环，处理超时、退避重试到期、`queued` 运行出队；
7. 应用启动时恢复（7.5）。

同步类节点（transform、switch、output、note）在 `start` 里直接完成并标记 succeeded，所以一次 `advance` 可以连续推进多步。

## 4. 节点类型规格

每种类型列出：配置、隐式端口、执行方式、成功/失败判定。所有节点都隐式带 `$in`（any，可多连，仅用于排序）、`$out`（any，值为 null）；除 `note` 外都带 `$error`（json：`{code, message}`）。

### 4.1 `trigger` 触发器

- 一个工作流**恰好一个**。没有输入；输出端口 = `WorkflowDef.inputs`（编辑器里两者同步编辑）。
- 配置：`{ sources: ("manual" | "automation" | "webhook" | "channel" | "subflow" | "cli")[] }`，仅用于展示和限制入口。
- 运行开始时直接 succeeded，输出值 = 运行入参（已按 schema 校验）。
- 外部来源（webhook、飞书消息）的入参在值上打 `untrusted: true` 标记，下游 agent 节点渲染时用随机边界包裹（复用 `start_automation_run` 的 `UNTRUSTED_PAYLOAD_<boundary>` 做法）。

### 4.2 `output` 输出

- 输入端口 = `WorkflowDef.outputs` 的子集；可有多个 output 节点（不同分支），运行结束时按节点定义顺序合并，后者覆盖前者。
- 立即 succeeded，值写入 `workflow_runs.outputs_json`。子流程的返回值就是这个。

### 4.3 `agent` 智能体

配置：

```ts
interface AgentConfig {
  target: { type: "agent" | "squad"; id: string };
  prompt: string;                 // 模板
  mode: "auto" | "plan";          // plan：先出计划，在节点会话里审批后再执行（现有 Plan 流程）
  maxRepairTurns: number;         // 输出不合格时自动追问次数，默认 2
  continueSession?: "never" | "same_node"; // same_node：循环/重试复用上一 iteration 的会话（保留上下文），默认 same_node
  fallbackTextPort?: string;      // agent 没有提交任何输出时，把最终回答文本写到这个端口（必须是 text/markdown）
  allowTaskCommands?: boolean;    // 是否允许 agent 在节点里 `multara task create` 派子任务，默认 false
}
```

隐式输出端口：`text`（markdown，最终回答正文）、`session_id`（text）。

**执行：**
1. 建会话：`chat_sessions.id = "wf-node:<node_run_id>"`（`continueSession=same_node` 且已有上一 iteration 的会话时复用旧会话 id），`target_type/target_id` = 配置的 target，`title = "<工作流名> · <节点标题>"`。
2. 关联需求与工作区：节点声明的每个槽位，写 `session_projects` 和 `session_workspaces`（`workspace_id` = 槽位的工作区行；fork 时用临时 worktree 的行）。这样执行器现有的 `workspace_context`（`executor.rs` 约 3316 行）会把 cwd 设成槽位目录，并把可写目录限制在这些目录里。没有声明槽位时走现有的 scratch 目录逻辑。
3. 写一条 user 消息，内容 = **节点简报**（4.3.1）；`agent_runs` 用 `ops::run::enqueue` 入队（`mode` 取配置）。
4. `workflow_node_runs.session_id` 记下会话，状态 running，`executor::dispatch`。

**完成判定**：在 `executor::finish` 的钩子里，当该会话满足「没有 queued/running 的 agent_runs」且「没有待审批的计划」（`crate::plan::latest_awaiting_plan` 返回 None）时，视为本轮结束。这与自动化判定会话结束的方式一致，天然覆盖小队（队长 + 成员 + 队长收尾）和 Plan 审批后的执行轮。
   - 若有待审批计划：节点状态 `waiting_human`，收件箱照常出现 Plan 审批（现有机制），用户批准后执行器自动入队执行轮，结束时再次判定。
   - 最后一个 agent_run 状态 failed/stopped 且节点没有提交过任何输出 → 节点失败 `agent_failed`。

**输出收集与校验**：
- 值来源：agent 在运行中通过 `multara node output`（第 8 节）提交，写入 `workflow_values`；`text` 端口取最后一条 assistant 消息正文。
- 校验：每个 `required` 输出端口有值、类型正确、`schema` 通过。不通过且 `repair_count < maxRepairTurns`：在同一会话入队一轮追问（「以下输出缺失或不合格：…，请用 `multara node output` 补交」），`repair_count += 1`；超限 → 失败 `output_invalid`。
- 只有一个 required 输出端口、类型为 text/markdown、且配了 `fallbackTextPort` 时，没提交就用最终回答文本兜底。
- agent 调用 `multara node fail --reason` → 节点直接失败 `agent_declared_failure`，不追问。

**会话可见性**：`wf-node:` 会话不进聊天侧栏列表（在会话列表查询里排除这个前缀，和处理 `automation-run:` 的方式一样），只能从运行视图点开；会话里仍可正常插话（用户的追加消息照常入队）。

**与现有机制的隔离**（必须改，否则会串流程）：
- `dispatch_mentions`：target 为 agent 的 `wf-node:` 会话里不解析 `@`（否则 agent 回答里写个 `@某人` 就被派活了）；target 为 squad 时保留，这是小队本身的工作方式。
- `maybe_resume_parent`：节点会话不建 task，不会触发；但若 `allowTaskCommands=true`，agent 建的子任务 `parent_task_id` 为空，子任务完成后通过 `workflow_node_runs` 找回节点会话，只写桥接消息，不触发父任务汇总。
- `conversation::save_id`：**保留**节点会话的 CLI 会话 id（不要像 `automation-run:` 那样跳过），追问轮和 `continueSession=same_node` 依赖它延续上下文。

#### 4.3.1 节点简报（`workflow/brief.rs`）

```
[工作流节点] {{workflow.name}} › {{node.title}}（第 {{iteration+1}} 轮，第 {{attempt}} 次尝试）

## 任务
{{渲染后的 prompt}}

## 输入
- spec（json）：见文件 /…/workflow-runs/<run>/<node_run>/inputs/spec.json
- feedback（markdown，来自「测试结果判断」）：
  <<<INPUT_feedback
  …内容（≤8KB 内联，超出给文件路径）…
  INPUT_feedback>>>
（外部来源的输入用 UNTRUSTED 边界包裹，并注明只能当数据读）

## 工作目录
- app（可写）：/…/worktrees/wf-xxx，分支 wf/req-to-release-3f2a，基于 main@a1b2c3
- docs（只读）：/…

## 你必须交付的输出
- spec（json，必填）schema：{…}
  提交：multara node output spec --json-file ./spec.json
- summary（markdown，必填）：一句话说明改了什么
  提交：multara node output summary --text "…"
做不到时：multara node fail --reason "…"

## 规则
- 不要 @ 其他智能体，不要创建任务（除非节点允许）。
- 不要 git commit / push，提交由工作流负责。
- 所有输出都提交后，用一两句话结束回答。
```

语言跟随应用语言（`tr!`）。

### 4.4 `script` 脚本

```ts
interface ScriptConfig {
  command: string;              // 模板；插值一律自动 shell 转义（见安全）
  shell: "default" | "sh" | "bash" | "pwsh" | "cmd"; // default：mac/linux 用 sh -c，Windows 用 powershell -NoProfile -Command
  cwd: { slot: string; subdir?: string } | null;    // null = 运行的临时目录
  env: Record<string, string>;  // 值为模板，可用 secret()
  successExitCodes: number[];   // 默认 [0]
  failOnNonZero: boolean;       // false：退出码不在成功列表时节点仍 succeeded，交给下游 switch 判断；默认 true
  parseStdout: "none" | "text" | "json" | "lines"; // 默认 none
  maxOutputKB: number;          // stdout/stderr 内联上限，默认 256，完整日志总在文件里
}
```

隐式输出：`exit_code`（number）、`stdout`（text）、`stderr`（text）、`log`（file，完整合并日志）、`ok`（boolean）、`parsed`（parseStdout≠none 时），以及聚合端口 `$result`（json：`{exit_code, ok, stdout, stderr, log, parsed?}`，方便整包连给 switch）。http、git 节点同样隐式带 `$result`，内容为各自全部隐式输出的合集。声明的其他输出端口来自 `$WF_OUTPUT_DIR/<port>.json` 或 `<port>.txt`（脚本自己写）。

注入环境变量：`WF_RUN_ID`、`WF_NODE_ID`、`WF_INPUT_DIR`（每个输入一个文件 `<port>.json`）、`WF_IN_<PORT>`（≤32KB 的输入直接放值，json 序列化）、`WF_OUTPUT_DIR`、`WF_WS_<SLOT>`（槽位路径）。

执行：后台线程 `crate::process::command` spawn，stdout/stderr 逐行写日志文件并通过 `workflow-node-log` 事件推给前端（运行视图用 xterm 回放）；进程句柄登记到引擎的 `active_scripts`，取消/超时时 kill 进程树。

### 4.5 `gate` 人工关卡

```ts
interface GateConfig {
  title: string;                         // 模板
  body: string;                          // markdown 模板，展示给审批人（可引用上游 diff 摘要、测试结果）
  decisions: { port: string; label: string; primary?: boolean; requireComment?: boolean }[];
                                         // 默认 [{approve,"通过",primary}, {changes,"打回修改",requireComment}, {reject,"拒绝"}]
  form?: JsonSchema;                     // 额外表单字段（如「发布环境」下拉）
  showDiffOf?: string[];                 // 槽位 key：审批卡片里附「查看改动」入口（打开 Monaco diff，基于槽位 base..head）
  notify?: { feishu?: boolean };         // 同时推送到总览会话绑定的飞书
  timeoutMinutes?: number; onTimeout?: "approve" | "reject" | "fail";
}
```

输出：每个 decision 一个分支端口（值 `{decision, comment, form}`）、`comment`（text）、`form`（json）、隐式 `exhausted`。

执行：
1. 节点运行 `waiting_human`；在**总览会话**（`wf-run:<run_id>`，见 5.3）插入一条 assistant 消息，正文为渲染后的 body，`quick_actions` 为各个 decision。
2. `QuickAction` 新增可选字段 `action`（`models.rs` 约 475 行 / `types.ts` `QuickAction`）：`{"type":"workflow.gate","nodeRunId":"…","decision":"approve"}`。前端点击带 `action` 的快捷操作时调用 `decide_workflow_gate`，不发送聊天消息；`requireComment` 的选项先弹出输入框。
3. 收件箱：总览会话的 inbox 条目状态置为 `waiting`、未读，标题「待审批：<gate 标题>」。
4. 在总览会话里**打字**也能决定：`send_message` 检测到 `wf-run:` 会话且有等待中的 gate 时，不派给 agent，而是按「通过 / 打回：原因 / 拒绝」或 decision label 前缀匹配；匹配不到则回复一条说明。飞书渠道绑定在总览会话上，所以在飞书里回复同样生效。
5. 决定写入 `workflow_gate_decisions`，节点 succeeded，`fired_ports = [decision.port]`，`advance`。

### 4.6 `switch` 分支

```ts
interface SwitchConfig {
  value: string;                        // 表达式，结果作为各分支端口的值；默认 "inputs.value"
  cases: { port: string; when: string }[]; // 按顺序求值，第一个为真的分支触发
  defaultPort?: string;                 // 都不为真时触发；未配置且无命中 → 节点失败 no_case_matched
  mode: "first" | "all";                // all：所有为真的分支都触发（并行），默认 first
}
```

输入端口自定义（常见一个 `value: any`）。输出端口 = 各 case port + defaultPort + 隐式 `exhausted`。同步执行。

例：`cases: [{port:"pass", when:"inputs.test.exit_code == 0"}, {port:"fail", when:"true"}]`。

### 4.7 `transform` 变换

`{ assignments: { port: string; expr: string }[] }`，每个输出端口 = 一个表达式的结果。同步执行。用于拼接、字段提取、构造下游 json。

### 4.8 `http` 请求

```ts
interface HttpConfig {
  method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";
  url: string; headers: Record<string, string>; body?: string; // 模板
  bodyType: "json" | "text" | "form" | "none";
  expectStatus: number[];               // 默认 200-299
  responseType: "json" | "text";
}
```

输出：`status`（number）、`headers`（json）、`body`（json|text）、`ok`。使用现有 `http_client.rs`（走 rustls + 系统证书），后台线程执行。

### 4.9 `git` Git 操作

```ts
interface GitConfig {
  slot: string;
  op: "commit" | "squash" | "push" | "merge" | "create_branch" | "diff";
  message?: string;        // commit/squash，模板
  branch?: string;         // merge：要合入的分支（常用 {{ nodes.x.outputs.branch }}）；create_branch：新分支名
  remote?: string;         // push，默认 origin
  setUpstream?: boolean;   // push
  skipVerify?: boolean;    // 跳过 hooks，默认读应用设置
}
```

输出：`head`（text）、`branch`（text）、`diff`（file，op=diff 时为 `base..head` 的 patch）、`changed_files`（json 数组）。复用 `git.rs` 的 `commit` / `push` / `merge_branch` / `compare_refs` 等函数。`squash` = `git reset --soft <base> && commit`，用于在交付前把自动提交压成一个。

### 4.10 `notify` 通知

`{ channel: "feishu" | "inbox"; text: string /*模板*/; to?: "run_owner" | string }`。飞书复用 `channel/feishu_send.rs`（发给总览会话绑定的会话/用户，或配置的接收人）；`inbox` 只在总览会话插一条消息并标未读。

### 4.11 `subflow` 子流程

`{ workflowId: string; version: "latest" | number; inputs: Record<string,string> /*模板，映射到子流程入参*/ }`

输入/输出端口自动与子工作流已发布版本的 inputs/outputs 同步。执行：创建子运行（`parent_node_run_id` 指回本节点运行，`trigger_source=subflow`），本节点 `waiting_children`；子运行结束 → 本节点按子运行结果 succeeded/failed，输出 = 子运行 outputs。工作区槽位：子流程槽位可配置「继承父运行同名槽位」（`project` 填 `{{ parent.ws.app }}`），继承时共用同一个工作区行与锁。递归深度上限 5。

### 4.12 `map` 并行遍历

`{ items: string /*表达式，必须得到数组*/; workflowId: string; version; itemInput: string /*子流程入参名*/; extraInputs: Record<string,string>; concurrency: number /*默认 2*/; failFast: boolean }`

对每个元素起一个子运行（子流程里可用 `item` / `index`），全部结束后本节点 succeeded，输出 `results`（json 数组，按下标对齐子运行 outputs）、`failed_indexes`（json）。`failFast=true` 时任一失败即取消其余并失败。Map 只接受子流程，不支持「画布上框一块区域」——子流程更容易单独测试和复用。

### 4.13 `note` 便签

纯展示，不参与执行，不能连线。

## 5. 运行如何进入系统

### 5.1 入口

| 入口 | 实现 |
|---|---|
| 工作流页「运行」 | 按 `WorkflowDef.inputs` 渲染表单（复用自动化页的表单组件风格），`start_workflow_run` |
| 自动化 | `automations.target_type` 增加 `'workflow'`；`start_automation_run` 里 `target_type == "workflow"` 分支：`prompt` 作为入参 JSON 模板渲染（可引用 `payload`），调用 `workflow::engine::start_run(source="automation")`。定时 / webhook / API 触发全部沿用现有 trigger 表 |
| 飞书 / Lark | 在已接入的聊天里发 `/flow <工作流名> <内容>`：内容填入声明为 `primary` 的入参（没有就填第一个），其余用默认值。运行记住来源聊天（`extra.channel`），审批通知发回该聊天，回复 `/approve`、`/changes <原因>`、`/reject` 即可审批。不改动渠道原本绑定的智能体会话 |
| CLI | `multara workflow run <id> --input key=value --input-json '{…}'`（agent 也能用它触发工作流，需在 `ensure_write_allowed` 登记为写命令） |
| 子流程 / Map | 引擎内部 |

### 5.2 运行开始时做什么（`engine::start_run`）

1. 取已发布版本（没有发布 → 报错「请先发布」）；`concurrency` 策略检查（`skip_if_running` 直接返回 skipped；`queue` 入 `queued` 状态由 tick 出队）。
2. 校验入参（类型 + schema），写 `workflow_runs`。
3. 建总览会话 `wf-run:<run_id>`（target = `settings.ownerAgentId`），写一条系统风格消息「工作流 X v3 开始运行」；用 `ops::task::attach_existing_session` 建一张任务卡（标题「<工作流名> · <primary 入参摘要>」），这样看板和收件箱都能看到这次运行。
4. 准备工作区槽位（5.4）。失败 → 运行失败 `workspace_prepare_failed`，已建的 worktree 清理掉。
5. 为每个节点建 `iteration=0, attempt=1, pending` 的节点运行。
6. `advance`。

### 5.3 总览会话与任务卡

- 总览会话承载：开始/结束通知、每个 gate 的审批消息、notify(inbox) 消息、失败原因。它**不会**派发给 agent（`send_message` 对 `wf-run:` 会话走 4.5 的 gate 解析）。
- 任务卡状态由引擎同步：running → `in_progress`；waiting（有 gate 等待）→ `in_review`；succeeded → `done`；failed → `blocked`；cancelled → `cancelled`。
- 点任务卡进入任务详情时，在详情顶部显示「查看工作流运行」入口，跳运行视图。

### 5.4 工作区槽位准备（`workflow/runtime.rs` `AppHost::prepare_slot`）

对每个 `WorkspaceSlotDef`：
1. 渲染 `project` 得到需求 id，按 `workspace` 名称找到需求下的源工作区行（`workspaces.session_id IS NULL` 的那批）。
2. `isolation`：
   - `worktree_new`：调用 `workspace::prepare(app_data, project_id, source_path, "worktree", …, base_ref, Some(branch), create_branch=true)`，分支名渲染 `branch` 模板；
   - `worktree_existing`：同上，`create_branch=false`；
   - `direct`：直接用源工作区，**启动前弹确认**（会直接改用户当前分支）。
3. 插入 `workspaces` 行（`session_id = "wf-run:<run_id>"`，`source_workspace_id` = 源工作区），记 `merge_flow::record_origin`，使现有「合并回原分支」流程对它可用。
4. 写 `workflow_run_workspaces(run_id, slot_key, workspace_id, base_commit, head_commit)`。

写节点执行前记录 `workspace_before`（每个写槽位 `git rev-parse HEAD`，加上 `git status --porcelain` 是否干净）；成功后若 `autoCommit`，执行 `git add -A && git commit -m "wf(<workflow slug>#<run short>): <节点标题>"`（无改动则跳过），记录 `workspace_after`，更新 `head_commit`。失败的节点**不自动提交**，现场留给用户看；重试时按 3.7 处理。

运行结束后 worktree 保留（用户要看结果、合并、推送）。运行删除时询问是否一并删除 worktree 和分支（复用 `workspace::remove_with_options`）。

## 6. 数据库

### 6.1 新表（`workflow/mod.rs` `migrate`，由 `database.rs` `migrate` 调用）

```sql
CREATE TABLE IF NOT EXISTS workflows (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  icon TEXT NOT NULL DEFAULT '',
  draft_json TEXT NOT NULL,
  draft_hash TEXT NOT NULL DEFAULT '',
  draft_updated_at TEXT NOT NULL,
  published_version INTEGER,
  enabled INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_workflows_slug ON workflows(slug);
CREATE TABLE IF NOT EXISTS workflow_versions (
  workflow_id TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  version INTEGER NOT NULL,
  definition_json TEXT NOT NULL,
  definition_hash TEXT NOT NULL,
  note TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  PRIMARY KEY (workflow_id, version)
);
CREATE TABLE IF NOT EXISTS workflow_runs (
  id TEXT PRIMARY KEY,
  workflow_id TEXT NOT NULL REFERENCES workflows(id) ON DELETE CASCADE,
  version INTEGER NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('queued','running','waiting','succeeded','failed','cancelled','skipped')),
```

### 6.3 启动恢复（`engine::recover`，应用启动时由 `runtime::start` 调用）

现有逻辑会把 running 的 agent_runs 标为 failed。工作流在其后：
- `workflow_node_runs` 中 `running` 的 script / http / git → `failed`，`error_code='app_restarted'`（随后按重试策略处理）；
- `running` 的 agent 节点 → 交给第一次 `advance`：其会话已无活动 run，按 4.3 完成判定（通常落到 `agent_failed` → 重试策略）；
- `waiting_human` / `waiting_children` / `pending` / `ready` 保持；
- 所有 `running`/`waiting` 的运行在应用启动后由 `workflow::engine::recover_all` 依次 `advance`。

### 7.1 模块结构

**引擎与副作用分离**：引擎的所有入口都是「拿着 DB 连接完成状态变更，返回 `Vec<Action>`」。需要外部能力的地方（时间、git、准备 worktree、密钥）通过 `Host` trait 获取；耗时的事（跑脚本、HTTP、Git 命令、派发 agent、发事件和通知）作为 `Action` 返回，由 `runtime::apply` 在释放 DB 锁之后执行，完成后再调用 `engine::complete_job`。这样同一套引擎在单测里用假 Host 驱动，覆盖了循环、审批、重试、超时、子流程等全部路径。

### 7.3 `engine::on_session_idle`

```rust
pub fn on_agent_session_maybe_idle(app: &AppHandle, session_id: &str) {
    let Some(node_run_id) = store::node_run_by_session(db, session_id) else { return };
    // 只处理当前节点运行；旧 iteration 复用会话的情况，以 node_run.status == running/waiting_human 为准
    if active_runs(db, session_id) > 0 { return; }
    if plan::latest_awaiting_plan(db, session_id)?.is_some() {
        set_status(node_run_id, "waiting_human"); emit; return;
    }
    let last = last_run_status(db, session_id);           // completed / failed / stopped
    if declared_failure(node_run_id) { return complete_node(.., Err(agent_declared_failure)) }
    let outputs = values::collect_agent_outputs(db, node_run_id, session_id); // CLI 提交 + text 端口 + fallback
    match values::validate_outputs(&node.outputs, &outputs) {
        Ok(()) => complete_node(.., Ok(outputs)),
        Err(problems) if last != "completed" => complete_node(.., Err(agent_failed(problems))),
        Err(problems) if repair_count < cfg.max_repair_turns => enqueue_repair_turn(problems),
        Err(problems) => complete_node(.., Err(output_invalid(problems))),
    }
}
```

`complete_node` 之后统一 `advance(run_id)`。

### 7.5 并发模型

- DB 仍是现有 `AppState.lock_db()` 单连接互斥；引擎在锁内只做读写，不做耗时操作（spawn、git、HTTP 都在锁外的线程里）。

- 后台节点线程完成后只调用 `complete_node`，由它拿锁写库再 `advance`。

### 11.4 编辑器交互要点

- 拖端口连线时：不兼容的目标端口置灰；连到祖先节点时自动识别为回边，仅允许从 switch/gate 发起，并立刻要求填 `maxIterations`。
- 节点上直接显示关键配置摘要：agent 显示智能体头像与模式；script 显示命令首行；switch 显示各分支条件；gate 显示决定按钮。
- 撤销/重做（Ctrl/Cmd+Z / Shift+Z）、多选、复制粘贴（跨工作流可用，粘贴时重新生成 id 并修正连线）、对齐、自动布局（elk layered，回边不参与布局）。
- 自动保存草稿（停止编辑 800ms 后 `save_workflow_draft`），顶部显示「草稿 · 未发布改动」与「发布」按钮；发布弹框填说明，展示与上一版的差异（节点增删、配置变化列表）。
- 「试运行」= 发布前用草稿跑一次：后端用草稿生成一个 `version = 0` 的临时版本（`workflow_versions` 中 version 0 每次覆盖），运行列表里标「草稿运行」。
- 「保存为模板」：选中节点 → 存成用户节点模板（端口、配置、提示词都带上）。

### 11.5 运行视图交互要点

- 节点颜色：pending 灰、ready 浅蓝、running 蓝（动画描边）、waiting_human 橙、succeeded 绿、failed 红、skipped 浅灰虚线、cancelled 灰斜纹。
- 有多轮/多次尝试的节点显示角标「第 2 轮 · 第 1 次」，点开抽屉可切换查看历史节点运行。
- 活连线高亮并在线上显示值摘要（悬停看完整值）；死连线淡化。
- 失败节点抽屉里有「从这里重试」（3.7）、「跳过并继续」（把该节点标 succeeded、输出手填，需确认）。

| 编写代码 | agent，写 `app` 槽位 | `spec`、`plan`、`design?`、`feedback?: markdown` | `summary: markdown`、`changed_files: json` | `feedback` 是回边端口 |
| 代码评审 | agent，读 `app` | `spec`、`diff: file` | `verdict: json({pass:boolean, issues[{file,line,severity,comment}]})` | 推荐用与编码不同的智能体/运行时 |
| 单元测试 | script，读写 `app` | — | 隐式 exit_code/stdout/log | `pnpm test`，`failOnNonZero=false` |
| E2E 测试 | script | `base_url?` | 同上 + `report: file` | |
| 测试结果判断 | switch | `value: json` | `pass` / `fail`（回边到编写代码） | `when: inputs.value.exit_code == 0` |
| 生成改动 diff | git(op=diff) | — | `diff: file`、`changed_files` | |
| 人工验收 | gate | `summary`、`diff?` | `approve` / `changes`（回边）/ `reject` | `showDiffOf: ["app"]` |

## 13. 安全

1. **脚本注入**：script 的 `command` 模板里所有插值默认经过 `shell_quote`（按所选 shell 的规则：POSIX 单引号转义 / PowerShell 单引号转义 / cmd 拒绝含特殊字符的值）。真需要原样插入时必须显式写 `{{ x | raw_unsafe }}`，校验器给 warning。推荐通过 `WF_IN_*` 环境变量和 `WF_INPUT_DIR` 文件传数据，而不是拼命令。
2. **不可信输入**：来自 webhook / 飞书 / 外部 HTTP 响应的值带 `untrusted` 标记（存在 `workflow_values` 的元数据里，沿 transform/switch 传播），进入 agent 简报时用随机边界包裹并注明只能当数据读。
3. **密钥**：值存密钥存储——把 `channel/secret.rs` 泛化为 `secret_store.rs`（命名空间参数：`channel` / `workflow`），macOS 钥匙串，其他平台 0600 文件；DB 只存名字。`secret()` 只能用在 script env、http url/headers/body；script 日志、http 响应、错误信息写库前做值替换脱敏（复用 `truncate_and_redact` 并加上已知密钥值的替换）。
4. **路径**：`multara node output --*-file` 的路径限制同 `ensure_description_file_allowed`；值文件只写在 `workflow-runs/<run>/` 下。
5. **direct 槽位**：直接改用户当前分支的槽位，启动运行前强制确认；push/merge 到受保护分支（`git::is_protected_branch`）的 git 节点，校验时给 warning，运行时若前面没有 gate 则拒绝执行。
6. **Plan 模式隔离**：Plan 轮次里 `multara node output` / `workflow run` 被 `ensure_write_allowed` 拒绝。

### 14.1 Rust 单元测试（`workflow/tests/` + 各模块 `#[cfg(test)]`）

| 测试 | 断言 |
|---|---|
| 线性 A→B→C | 顺序执行，值正确传递 |
| 并行 + join all | B、C 并行，D 在两者都完成后执行 |
| join any | 第一个到达即执行，后到的不重复触发 |
| switch 跳过传播 | 未选分支的整条链 skipped，汇合节点仍执行 |
| required 输入只来自死边 | 节点 skipped，reason 正确 |
| 回边循环 | fail 两次后 pass：code 有 iteration 0/1/2，回边值传入 feedback |
| 循环耗尽 | 达到 maxIterations 后走 exhausted；未连线则运行失败 loop_exhausted |
| gate 打回回边 | changes 决定触发新 iteration，comment 传入 |
| 自动重试与退避 | retry_at 计算正确，tick 到期后新 attempt |
| 手动从节点重试 | 节点与后代新 attempt，上游不重跑 |
| onError=continue | $error 端口活、其他端口死 |
| 取消 | 所有非终态 → cancelled，假执行器收到 cancel |

| 启动恢复 | running 的 script 节点 → failed(app_restarted) → 重试 |

### 15.1 验收标准

1. 能在画布上从空白搭出附录 A 的工作流，校验无 error，发布 v1。
2. 手动运行：读需求节点在节点会话中调用 `multara node output spec --json-file …` 成功，schema 不合格时 CLI 当场报出字段路径；编码节点在 worktree 中改代码，自动提交一次；单测第一次失败时自动回到编码节点，`feedback` 中带失败日志；第二次通过；评审 agent 输出 verdict；验收 gate 在收件箱和飞书中出现，「打回修改」带评论回到编码节点；再次通过后压缩提交、推送、创建 MR，`output` 节点给出 MR 链接。
3. 运行过程中退出应用再打开：等待中的 gate 仍可审批，运行继续。
4. 任一节点失败后「从这里重试」只重跑该节点及下游。
5. 自动化定时触发工作流、webhook 带载荷触发工作流，两者都在运行列表和看板中可见。
6. 小队、父子任务、普通聊天、自动化（agent/squad 目标）行为与改动前一致（现有测试全绿）。
7. 五种语言界面完整，无未翻译键。

## 16. 实现时相对初稿的调整

| 项 | 初稿 | 实现 | 原因 |
|---|---|---|---|
| 工作区 | `workspace` 端口类型 | 工作流级「工作区槽位」，节点声明读/写 | 工作区是共享状态；槽位便于统一加锁、自动提交、按节点回滚 |
| JSON Schema | `jsonschema` crate | `schema.rs` 子集校验器 | 依赖轻；节点输出只需要常用关键字，且要给 agent 看得懂的字段路径 |
| 飞书入口 | 渠道目标可选工作流 | `/flow <工作流名> <内容>` 启动，`/approve`、`/changes`、`/reject` 审批 | 不改渠道表结构，也不占用聊天原本绑定的智能体会话 |
| CLI 触发 | 直接开始运行 | 写一条排队的运行，应用定时器 30 秒内开始 | CLI 进程没有应用句柄，跑不了脚本节点和事件 |
| 引擎结构 | 引擎直接执行副作用 | 引擎返回 `Action`，`runtime::apply` 在锁外执行（见 7.1） | 可在单测里用假 Host 驱动全部路径 |
| 写节点前的脏工作区检查 | `workspace_dirty` 错误 | 未做；写节点开始时只记录 `workspace_before` | 重试时可选择回滚到该提交，已覆盖主要场景 |
| 运行用量 | 按节点汇总 token 与费用 | 运行详情按节点汇总 agent 运行次数与耗时（`RunDetail.usage`） | token/费用仍在统计页按会话查看；按节点细分留待后续 |
